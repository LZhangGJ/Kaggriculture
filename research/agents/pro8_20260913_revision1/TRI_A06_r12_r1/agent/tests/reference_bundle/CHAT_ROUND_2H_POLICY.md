# ChatGPT 6 Pro 单轮任务预算

用户要求：派发任务必须考虑会话执行环境的实际CPU、内存及预计工作时间，单轮迭代总用时不得超过2小时。

适用于原8位作者之后的每次派发，也约束当前未结束的源码轮次。原始派发开始计时，同版补充、失败续接不重置时钟。完整本地比赛由中控执行，不计为作者环境可承担的默认工作量。

每次派发必须明确：原始开始时间、120分钟截止、候选身份、要解决的单个结构问题、可交付范围、资源探测/试运行预算、工作/验证/打包分配及到时退出方式。

先用不超过5分钟的环境检查或最近同一有效环境的原始记录确认：Python/编译器版本、CPU affinity/可见CPU、cgroup CPU quota（不能只把os.cpu_count当可用核心）、cgroup内存上限及当前使用量、MemAvailable、可用磁盘。读不到配额时注明未知，保守使用1进程，不能假定宿主机总CPU/内存都归会话。

用已有实测或有明确timeout的短编译/少量合法历史观测试运行测量墙钟时间与峰值RSS。只有确实并行计时验证过才能按并行效率折算。预计测试时间=样本耗时×计划规模，并为编译、读材料、打包、传输和工具波动留足余量；数据不足时保守估计，不以模型主观速度作承诺。

并行度取有效CPU及内存双重约束；给系统和打包留至少30%内存余量，避免OOM和不受控多进程。每个子任务的timeout不得越过总截止。不得为测资源而启动完整880局或PASS。

一般目标：前90分钟完成有依据的单项源码修改与必要离线正反例；最迟100分钟进入交付，预留20分钟打包和工具故障余量。更短轮次根据实测缩减。到截止前必须交出真实源码检查点、当前匹配库（如有）、BUILD、原始日志、已完成/未完成项、资源规模与实测耗时；失败也交付实际文件，不冒充验证通过。下一轮基于该检查点另行安排，而非继续扩大当前轮次。

历史执行示例（该源码轮次已结束）：A08 r11从2026-09-12T15:09:14.919Z开始，硬截止2026-09-12T17:09:14.919Z；15:22同版故障续接不重置。90分钟节点16:39:14.919Z，100分钟打包节点16:49:14.919Z。作者最终核验记录16:09:20Z，本地下载完成16:16:41Z，均在原截止内；具体资源和身份以feedback/A08_r11_RECEIPT_REVIEW.json为准。

各轮当前起止时间、状态和资源证据记在STATE.json的chat_round_resource_budget.active_rounds；其中已关闭轮次作为历史记录保留，不能按字典名推断仍在执行。以原消息实际提交时间和已派发截止为准，不从本文件读取时间重新起算。

本地冻结的比赛源、native、seed、协议和运行器不因作者预算而修改。
