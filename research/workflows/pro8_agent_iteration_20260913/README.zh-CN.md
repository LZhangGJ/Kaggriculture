# Kaggriculture Agent 迭代工作流

[English version](README.md)

更新日期：2026-09-13。本文总结中控与 ChatGPT 6 Pro 作者协作的实际流程，以及当前三条策略血统的验收协议。文末成绩是该日期的快照，不是实时状态。

## 目标与分工

通过「源码修改 → 本地实战 → 败局分析 → 回传作者」反复迭代，使当前三个 Agent 各自在指定对手池中的**总体严格胜率超过 85%**。

最初由八个独立的 ChatGPT 6 Pro 会话参与探索；当前集中迭代 **A08 r11、A06 r6、A06 日历版 r12**，分别使用三个作者会话。每条血统延续自己的父版，版本关系必须明确。

| 角色 | 职责 |
| --- | --- |
| 中控：本地 Codex | 维护版本、状态和截止时间；准备源码与败局证据；派发任务；下载并核验交付；冻结测试输入；执行和复核比赛；发布成果并回传下一轮反馈。 |
| ChatGPT 6 Pro 作者 | 实际阅读源码和证据，查找具体原因，修改并编译策略，在资源预算内完成验证，按时交付可运行 ZIP。 |
| 本地评测器 | 使用固定的官方引擎和隔离进程执行完整比赛，保存结果与回放，为验收提供证据。 |

当前以实战胜率验收，平均终局现金作为诊断指标。此前的现金门槛和打空气测试已不再是验收条件。

## 一轮完整流程

1. **确认当前检查点。** 读取权威状态、上一轮成绩、精确父版源码／配置／动态库，以及实际运行中的进程或会话。保留已完成轮次；一次状态读取超时不能成为重复启动任务的理由。
2. **分析败局，同时保护险胜。** 从完整结果中选公开对手败局、R2 败局、接近胜利的败局和险胜对照，按购销、生产、劳动力、购地、成熟时间和期末库存核对现金，区分估值、滚动排程和底层执行的问题。
3. **派发有边界的作者任务。** 写明父版与下一版身份、证据、具体假设、修改范围、资源预算、开始时间、截止时间、验证范围与交付要求。三个血统分别派发，要求实际修改代码并交付下载包。
4. **下载并核验交付。** 保存原始 ZIP 和 SHA-256，检查文件完整性、生产源码、配置、匹配动态库、构建说明、默认入口及必要正反例。区分中控独立验证和作者自述。
5. **先冻结，再抽种子。** 固定候选源码／动态库、官方引擎、对手、运行器和协议，收集作者开发用 seed 及历史预留记录，再一次性抽取下一轮共享的 64 个 seed，比赛前保存不可随结果修改的计划。
6. **本地运行完整面板。** 执行全部 seed × 对手 × 座位组合，保存每局结果、错误与回放。同一时间仅运行一个完整评测面板；作者的小样本测试另行记录。
7. **复核、发布、决定下一轮。** 独立检查完整性、终局、哈希和统计，将精确版本、英文简介和评测证据发布到 GitHub。未达标的血统继续收到具体败局反馈，形成新版本后换新 seed 复测。

优化对象包括经济规划、滚动排程和底层执行。采用动态规划时，应明确状态、时域、约束、优化目标和回退策略，并通过闭环实战确认收益。

## 作者单轮最多两小时

120 分钟包含阅读、分析、实现、编译、验证、故障处理和打包。补充消息不重置计时；中控本地完整比赛是单独的工作量。

| 时间预算 | 必须完成的工作 |
| --- | --- |
| 前 5 分钟 | 检测 CPU affinity、cgroup CPU 配额、内存限制与当前占用、可用内存和磁盘、Python／编译器版本。上一轮环境信息只作为历史记录。 |
| 早期 | 对受 timeout 限制的编译和代表性试运行计时，记录墙钟时间与峰值 RSS，估算可完成的工作量，计入工具波动和打包开销。 |
| 90 分钟前 | 完成有依据的源码检查点及必要验证。 |
| 100 分钟前 | 开始打包和最终检查。 |
| 120 分钟前 | 交付真实检查点及原始证据，说明失败和未完成项。 |

CPU 有效配额未知时保守使用一个进程；并行度同时受 CPU 和内存约束，至少预留 30% 内存。前几十步的短测试不能直接证明完整比赛耗时。所有子进程 timeout 必须落在本轮剩余预算内。

## 正式本地比赛设置

| 项目 | 当前协议 |
| --- | --- |
| 候选血统 | A08 r11、A06 r6、A06 日历版 r12；每次改版均冻结身份 |
| 种子来源 | 已公开的 representative 256 个 seed 与 stress 128 个 seed |
| 抽样方法 | 从两个池剩余可用 seed 的并集中，均匀、不放回地抽取**合计 64 个**；三个候选共用同一次抽样 |
| 排除范围 | 以往预留或测试过的 seed，以及作者报告的全部开发 seed |
| 对手 | 固定的 11 个公开条目，加真实原始 AFS R2：`submission_56149565` |
| 座位 | 每个 seed／对手组合都交换座位，分别执行座位 0、1 |
| 比赛长度 | 官方完整比赛，719 次状态转移 |
| 样本量 | 每版 64 × 12 × 2 = **1,536 局**；三个版本共 **4,608 局** |
| 胜局定义 | 严格终局胜利；平局不算胜利 |
| 验收门槛 | 每版总体胜率 >85%，即至少 **1,306 / 1,536 胜** |
| 辅助报告 | representative／stress、逐对手、公开 11 合计、R2、座位、终局现金及错误 |

十二个固定对手条目为：

`soil_v219g`、`moon_v215`、`flexon_v5`、`market_smart_v8`、`nagatakengo_v70`、`aurax_reactive_v1`、`thomas_955_v2`、`shop0909`、`aurax_shop_v2`、`seven_turn`、`ahmed_v27`、`submission_56149565`。

按用户指定条目等权统计。部分公开条目共享代码，不能把它们描述为十二个独立策略家族。最初本地入门 Agent 和其它作者版本不属于当前验收对手池。

当前使用的是**混合开发面板**。封存 Holdout 的具体 seed 不可读取，因此不能宣称是在封存 Holdout 上验收。保留 representative／stress 标签；每次随机抽样的两类数量可以不同。不得看结果后重抽，也不能在种子不足时默默复用；剩余可用 seed 不足 64 个时，先取得新的种子来源。

当前运行器为策略使用独立的新进程，不向策略观测暴露环境 seed，并设置响应看门狗。本地测试设置本身不证明符合另一个比赛平台的运行时限。

## 证据与反馈规则

- 保留预先声明的完整分母。未完成对局、错误和缺失行必须显式报告，不能删除后宣称验收通过。
- 检查源码／动态库／引擎／对手／协议哈希、seed × 对手 × 座位的完整组合、所有终局和回放哈希，再从原始结果行独立复算总体与分组指标。
- 对精选反馈局，用固定官方引擎重放已保存的双方动作并核平现金账。这只能验证原局记录，不能替代改版实战。
- 资源允许时，在同 seed／对手／座位上配对测试父版和候选，纳入险胜保护，并保留所有失败。复用败局 seed 属于开发诊断，不算 fresh 验收。
- 策略动作变化后，继续接原回放的未来不能构成有效反事实；必须让双方策略闭环运行。
- 生产策略仅使用合法的当前公开观测和己方私有状态。不得按隐藏 seed、对手身份、未来动作脚本或对手私有状态查表决策。
- 源码及败局证据按已获授权范围传送。对手源码和双方完整私有模拟状态需要相应范围覆盖；可以准备只含己方可见信息的精简反馈包。被拒绝的上传不能记为已派发任务。

当前准备的第二轮反馈每条血统包含七个精选局：五类败局和两个险胜对照。每局已在本地验证 719 次转移及 60 个玩家日的现金核算。

## 交付与 GitHub 发布

作者交付应包含入口、全部生产源码、固定配置、匹配的 Linux x86-64 动态库、离线构建说明、编译命令／flags 和源码／动态库哈希、必要检查、原始验证与资源耗时日志、英文 README，并如实说明失败和局限。

中控保存原始 ZIP、独立核验收据、冻结计划、机器可读成绩、逐局结果和回放身份。新版本发布到新目录，保留旧版及其报告；推送后核对远端提交和文件字节。编译通过、某个有利子集或作者自报的父子对打成绩都不能替代完整对手池验收。
