# P16–T3R1 + TakeoverRepair R1 合并实验

日期：2026-09-10。状态：**源码合并、重编译及小面板完成；不是已通过泛化晋级的冠军。**

## 1. 版本身份及结论

底版是 `Kaggriculture_P16_T3_ExecutionAligned_R1_20260910.zip` 中的 **P16–T3 ExecutionAligned R1**，不是早期基于R2的 `T3_ExecutionRepair_R1`。捐入修复来自 `Kaggriculture_P16_TakeoverRepair_R1_20260910.zip`。

实际只改动底版的三个业务源码文件：`policy/triad.hpp`、`policy/executor/policy.hpp`、`policy/bridge.cpp`。`MERGE_vs_T3R1.patch` 为完整差异。保留原38项配置、P16编译宏、动物预测noipa边界、T3运输/维护/实收检查及销售状态快照。没有改变对手程序、裁判、候选经营参数或固定开局路线，也未提交Kaggle。

本轮主面板新增实时对战264局：**3seed × 11对手 × 双座位 × 2开局 × 2版本**；每个版本每种开局66局，132个配对。没有运行1400局，也没有扩大到后五种子。所有主面板在候选冻结后一次完成，之后没有依据输赢继续调参。

## 2. 实际合入的三项修复

### 2.1 维护营运资金门

当已有喂养义务、当前饲料和现金不足时，尝试处理真实可达的物料抵押品，按真实单位动作收取/入库/出售，再补料。保护任务已承诺的物料，下一次从实际观察核对成交再重排。不制造现金、不赠饲料、不重写动物饥饿状态，不识别十二甜瓜或对手身份。

接入顺序为：真实盘面日规划 → 安装T3所用的独立销售快照 → 维护融资门 → 原生T3实收/维护/运输修复 → 真实市场指令。融资阶段提前返回时，后续T3状态不会因此被替换成旧P16状态。

### 2.2 日内追加投资改为当前剩余资产估值

在当前库存和当前在产资产上计算剩余投入产出，避免继续直接使用早晨完整组合；保留已经采用的当日FEED/CARE/施肥等承诺。沿用捐入修复的范围：**所有已采购尚未落地项目、在途货物精细到仓时间和跨日融资没有完整统一建模**，不能称作精确实时全账本。

### 2.3 资源过滤诊断

加入 `input_rejected_atoms/feed/fertilize`，计入整条FEED被资源过滤成空的情况。计数是最近一次预留阶段诊断，不是整季失败率。保留T3原只读 `td_repair_debug`，再增加 `td_obligations_json`；运行配置ABI仍为38项。

捐入包中已关闭的强制当天交付、提前收成熟作物、额外雇工候选及期限优先等实验未合入；`proposals.hpp` 相对T3R1逐字节不变。T3原有三类修复开启，`P16_WORKING_CAPITAL_GATE=1`、`P16_LIVE_REMAINING_VALUE=1` 显式写入编译配置。

## 4. 维护问题未复发，新的退步发生在后续经营

十二甜瓜接管次日（step48），T3R1有60/66局只剩一头牛，6局保留两头；合并版66/66均保留两头。默认开局两版66/66局均保留原三头牛。没有声称整季所有维护都已最优或全部动物存活。

正向样例 `2609178000 / ahmed_v27 / opponent_seat=0 / m12`：T3R1分差−3273，合并版+12639。

为检查合并为什么不如单独接管版，本轮对 `2609178002 / soil_v219g / opponent_seat=0 / m12` 另生成一次重复轨迹（不计新增强度样本）。单独接管修复终局+4603，合并版−634。两份完整联合动作的首个差异在 **step360，游戏day15，即第16天**；此前step0..359完全一致。首个不同指令：单独版买1份甜瓜种子和3份番茄种子、雇6人；合并版不买这份甜瓜种子、买3份番茄种子、雇7人。收肥料、出售16份肥料及买12份小麦相同。

因此，这一例不是step24融资或漏喂重新坏掉。代码中日级候选会调用完整执行器做条件前瞻，所以加入T3执行修复也可能改变上层候选选择，而不是只在选定方案末端少走几步。**这是可由调用关系支持的解释，但本轮没有对T3三个开关逐个进行因果消融，不能把终局损失全部归给某一次HIRE或少买一份种子。** 原轨迹、重复轨迹和首个分歧保存在 `evidence/diagnostic/`。

## 5. 历史数据与本轮测试的边界

T3R1和合并版264局均是本轮实时运行，719步完整结束，0运行异常。对手随当前观察响应，不是固定录像回放。

单独接管修复的132条对照来自用户提供的上一轮包（`references/takeover_previous132.json`），没有重新运行全132局。已逐文件确认双方使用的对手和裁判源码/资产完全一致；另外本轮实际重跑一个默认和一个十二甜瓜案例，现金、胜负、动作哈希、step48动物数都与归档一致。该两场只作为历史证据的复现检查。

本轮没有重跑90场天梯败局，不能沿用过去P16–T3或TakeoverRepair的成绩作为此合并版天梯结果。没有运行后五种子、没有新增独立留出集，没有做线上资源/ABI/schema认证。

## 6. 工程验收

- 原T3执行合约30项、捐入接管合约28项、合并交互合约38项全部通过；另通过P16首日供给/私有信息隔离/次日清除检查。38项交互合约含逐时动作槽断言，不是38个独立随机场景。
- 合并交互夹具在真实资金26、3份小麦的接管状态下，完成4次FEED；原4只动物均保住，没有欠资雇工，也没有制造现金。销售快照和条件预演副本不修改真实控制器状态。
- 从交付目录调用实际 `build.py`，GCC14.2重新构建得到与受测产物**相同SHA256**。
- 两条官方完整轨迹回归：1414次由Agent生成的动作比较，另24个固定开局动作比较，共1438次状态转换；不能把24步外部开局说成自主经营。
- 把旧T3R1库误当合并库送入行为门，在step24被拒绝。
- 将新增两项行为修复关闭，仍保留合并源码中的无行为诊断，重新编译后通过原T3R1三条完整轨迹，共2157步动作回归。这是分支可回滚证据，不是完整空间等价证明。

## 7. 本地入口与小面板

Linux x86-64 / WSL2、Python标准库及C++20编译器；没有Python第三方依赖或联网运行依赖。解压进入根目录：

```bash
python3 verify_package.py
python3 check_binary.py
python3 build.py --cxx g++ --out build/local.so
```

根目录 `main.py::create_agent()` 为每局创建独立实例，或使用 `main.py::agent`。默认明确加载 `policy/merged.so`。不要直接调用旧 `policy/agent.py` 默认单例（其历史默认文件名仍是agent.so），不要只换动态库而混用外部包装器。外部开局之后接管应使用新创建的实例，不复用前局句柄。

先比较默认开局（每版66局）：

```bash
python3 evaluate.py --out runs/native3 --opening none --seeds 3 --workers 3
```

再比较十二甜瓜（每版66局）：

```bash
python3 evaluate.py --out runs/melon3 --opening m12 --seeds 3 --workers 3
```

`--opening both` 可一次运行上述四组，共264局。默认比较 `merged,t3r1`；可用 `--versions merged,t3r1,takeover` 显式增加单独接管版，但会增加计算量。`--versions merged --binary build/local.so` 可测试本机重编译库。

同目录将 `--seeds 3` 改成 `--seeds 8` 只补尚未运行的5个种子，达到每个开局、每版、每对手16局。脚本拒绝超过8种子或3进程，拒绝混合库、配置、开局、裁判、对手和评测源码续跑。这里提供续跑能力，**本轮没有实际续跑后五种子**。由于现有八种子均已被旧实验使用，续跑也不能称为全新独立留出。

十二甜瓜的24步前缀只由 `arena.py` 读取，策略库及main.py不读取它；第24步起完全自主接管。`build.py`不会自动启动对战面板。

## 8. 使用建议

保留为独立的合并开发候选，不覆盖T3R1或单独接管版。默认开局值得继续做小规模独立验证；十二甜瓜目前不应替换单独接管版。需要后续验证的是执行修复如何改变长期候选的真实收益，而不是进一步无条件堆叠更多末端修补。
