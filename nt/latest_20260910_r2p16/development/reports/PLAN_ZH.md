# R2：11 个公开实时对手强化

## 目标与边界

用户授权：下载新 7 个方案，加此前 4 个，原 R2 各打 200 局；复盘真实败局，修复不足，最终在独立未见种子上对 11 对手等权平均胜率至少 90%。这是平均目标，不擅自改成逐对手 90%。不自动 public 提交或 Git 推送。

新方案：Soil V219G、Flexon Most Powerfull Route、Tetsutani Market Smart、Moon V215、Nagatakengo V5.9、Aurax Reactive Router（不是已测的 Shop Reactive V2）、Thomas 95.5% Replay Routing。

旧方案：Shop Router 0909、Aurax Shop Reactive V2、Seven-Turn Rescue、Ahmed notebookfea7d71a35。冻结版本，不能在调优过程中换弱对手。旧结果只有源码、R2、规则和种子完全一致才复用。

## 1. 下载与入口核查

- Kaggle 原 notebook、版本元数据、来源链接、SHA256 和实际运行文件分别保存。
- 不执行 notebook 的安装、上传和整本演示单元；静态提取原 Agent。
- 对压缩包校验路径；保留依赖文件及原作者注释。
- 首种子双座位完整局与重复重置检查；任何运行失败不算赢。

## 2. 冻结原版基线

- 官方 1.32.7 实时裁判；R2 使用此前验收过的原 C++ 二进制。
- 原 Python 公开对手实时响应，而非回放其固定对局动作。
- 100 种子 × 双座位 = 每对手 200 局，共 2,200 局；旧四个允许严格复用。
- 开发种子：2609110000–2609110099。每局保存双方全部动作、每日真实状态、现金、分差、运行错误、延迟。
- 最多 16 个 CPU 进程；先测实际吞吐，不因旧的全原生路线对打速度而冒称本次速度。

## 3. 败局与胜局一起复盘

按对手、商店组合、座位和经营模式分组；记录：开局投资→扩地与用工→首次大回款→转产→交付与销售→终局。区别硬执行错误、资金链问题与经济取舍。

重点检查但不预先判定根因：投产批次晚、购买与明日维护争用现金、收获/仓容/销售不协调、市场需求与新增供给失配、对手已公开产能未纳入预计收益、多人接力和跨日义务遗漏。

每种修复必须有完整重跑证据。不能以某一局的会计差额当作修复后的因果收益，也不能只验证失败局不跑既有胜局。

## 4. 修复与组合

- 冻结原 R2；新实现和配置在本实验目录，不覆盖已提交版本。
- 修复做独立开关，既测单项也测有关联的组合。
- 第一轮开发面板用于快速筛选，随后回跑全 11 对手开发面板。
- 只读取合法当前信息与己方持久计划；不使用对手 ID、seed、隐藏库存或未公开未来商店。
- 不把搜索到的单 seed 最优动作表写成策略。

## 5. 冻结候选并验收

独立最终种子预留：2609130000–2609130099。修复冻结后才使用；若看过结果又调参，此批即降为开发集，另留全新最终种子。

最终至少 100 新种子 × 双座位 × 11 对手。报告逐对手胜/负/平、严格胜率、平均/中位分差、现金分布、原败转胜和原胜转败；对原 R2 同批配对。平局不计胜。11 个对手等权平均胜率 >=90% 才算经济目标达标。

另外报告种子级相关性及胜率不确定性、完整 719 步率、无异常、动作延迟与官方运行兼容性。未达标时保留最佳候选和未解决失败模式，不能用理论 Oracle 或开发最高分代替最终验收。
