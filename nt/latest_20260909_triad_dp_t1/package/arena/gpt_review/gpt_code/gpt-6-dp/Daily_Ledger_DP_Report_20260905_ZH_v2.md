# Daily Ledger DP：独立规则代理与实测报告

日期：2026-09-05。最终策略为本次开发内部候选 v12；以下简称 **Daily Ledger DP**。

## 1. 结论

## 2. 测试口径

采用附件默认配置：10×10农场、初始现金3,000、24小时/日、30天、`episodeSteps=720`。官方解释器在 `step >= episodeSteps - 2` 时结束，因此每局包含**720个记录帧、719次实际决策**，不是提前终止一回合。最终结算严格使用真实现金；不计土地、动物、作物或库存的估值。

对手每一步只有 `PASS`，市场订单始终为空，不雇工、不种植、不交易。100局对手终局现金均为3,000。每组两边座位各25局。无丢弃失败种子，无对手镜像策略，无按种子选策略。两组种子范围和策略SHA256在开始评测前写入 `results/v12_test_protocol.json`。

主测试与复核调用提交入口 `agent(observation, configuration)`，使用文件内默认参数，没有评测器专用策略分支。官方解释器读入种子后会把 `configuration.seed` 清空；策略不能访问环境对象或随机事件脚本。策略文件仅导入标准库和NumPy，不导入模拟器、Replay、G001或其他策略。

早期失败结果没有删除：v4的50局均值181,981.56；v7两组50局分别187,753.66和187,222.52，均未达标。这些版本和结果保存在 `history/`。最终v12没有把这些旧测试集重新命名为新验证集。

## 3. 独立实现范围

策略代码在本次任务中独立编写。复用部分仅为附件提供的官方解释器、官方规则常量和CPU测试宿主；没有移植公开Notebook/G001/v6的策略控制器、开局表或路线库。参考Replay仅用于检验CPU宿主是否重现官方状态，不进入新策略的决策、拟合或训练。

默认开局动作可能在不同种子下相同：开局可见状态相同，确定性规划器自然给出相同解。这与硬编码整季路线不同。后续组合由真实商店、市场库存、现金、已建资产及剩余时间重新计算。例如在最终100局的 `day=12` 清晨，牛的数量范围为3–21、羊为4–31、草莓为2–43；这些是实际状态，不是外部路线编号。

## 4. 每日规划做什么

### 4.1 五条预测量与现金影子价值

每个候选产业数量产生五条按日展开的预测量：产出、饲料需求、肥料需求、操作量、需要访问的地块数。预测只使用当前公开市场和已出现商店；未解锁商店使用规则给出的均匀期望，不读取真实未来。

现金紧张且仍有扩张空间时，提高远期现金的折现率，重视较早回款。现金充裕或地块已接近满载时，该附加折现趋近零。这个量由当前现金和已占用地块比例决定，不是“第几天必须买几只动物”的日程表。

未来重复种植所需种子的费用，也按预计付款日期折现，不能一边折现未来收入、一边把整季未来种子费用全部提前扣除。该修正连同现金影子价值构成最终v12与前版的主要差异。

### 4.2 数量、土地和预算DP

对每种作物、动物枚举购买数量。单次条件DP的状态是“已处理产业、使用新增地块数、使用现金预算”，现金粒度为10；土地解锁费用单独枚举后比较。

其递推为：

`D_i(t,b) = max_k [ D_(i-1)(t-k,b-k*c_i) + V_i(k | 其他产业候选) ]`。

数量价值不是“当前单价×总产量”：要计算供给对未来市场价格的影响、饲料和肥料输入，以及未来操作开销。最多进行三轮条件重计价，重新计算组合共享的小麦、肥料及工作量成本，然后按整个候选组合的估值选解。

**精确的是每轮离散条件价值表上的DP，不是整个随机经营博弈的全局最优解。** 候选重计价、未来市场和线路成本仍是近似。程序没有在线调用官方解释器做整季搜索，也没有读取真实未来作事后选优。

### 4.3 非线性工人成本

劳动费用按官方斐波那契雇佣序列近似计算，而不是把所有新增操作都按一个固定廉价单价估算。预测访问次数也进入用工需求，使大量资产同时需要服务的组合付出更高代价。

实际雇工仍由当日任务量决定，普通日上限15名，末日最多17名；不是全季固定雇满。线路使用插入式启发式分配，并在真实观察上逐步执行，而非声称线路也已被全局最优求解。

### 4.4 收获容量DP与独立任务执行

当天的收获、收肥候选通过容量背包选择，价值中包含过期和阻塞下一次生产的代价。它是回仓吞吐量的代理预算，**不是精确的逐小时仓库排程**。

执行器把HARVEST、COLLECT_FERTILIZER、FEED、CARE、FERTILIZE、WATER拆成独立动作条件。没有“某工人拥有某株植物一生”的约束；工人可以接手其他工人之前种植的作物。缺少种子不会删除收获，缺少小麦不会删除收肥。缺肥时不让一趟临时回仓绕路阻塞整条路线上的生存浇水；每个动作仍检查实际库存和地块状态。

同回合种子和取货有共享预留，避免多个工人争用同一份库存。最终一天为返仓与出售预留时间；单位先入仓、市场后执行，所以同回合入仓的货物可以立即出售。满仓时优先用不会销毁余货的PLACE，而不是盲目DROP。

当前销售仍以保护必要投入后的及时变现为主，**没有实现完整的SELL_NOW/HOLD市场博弈DP**；不把这项未完成能力计入本版本成果。

## 5. 验证与运行时间

- 13项确定性语义测试全部通过，覆盖价格曲线、五种作物生命周期、缺种仍收获、缺饲料仍收肥、缺肥不阻塞浇水、跨工人收获、共享种子预留、末日同回合入仓出售、满仓安全放置、护理结算顺序、回合边界及入口重置。
- 附件10份参考完整Replay的**7,190次转换**与冻结官方状态一致，验证CPU宿主，不加载生成这些Replay的旧策略。
- 最终100份新动作记录再由原始解释器独立重放：**71,900次转换、3,000次清晨状态核对**通过；逐局现金、资产计数、商店、仓库、价格和终局结果与评测记录一致。
- 最终100局合计没有动物逃逸；仍有仓库溢出370件，即平均3.70件/局。未声称所有非PASS动作都实现了零无效操作，也未声称执行器已完美。

本地环境为Python 3.13.5、NumPy 2.3.5、Linux、4个CPU工作进程，`OPENBLAS_NUM_THREADS=1`。100局决策均值为 3.540 ms，观测到的最大值为 **357.153 ms**，发生在种子43091、座位1、`step=264 / day=11 / hour=0`。

对该局另行使用无NumPy预加载的单进程冷启动测试：模块冷导入 42.419 ms；导入加第一次决策 194.629 ms；最慢决策 221.065 ms；进程最大RSS约 29.83 MiB。该局终局现金仍为181,732，与原评测一致。

附件的 `actTimeout=1` 秒。上述本地测量低于1秒，但CPU宿主不是Kaggle沙箱，也不等于已获得线上超时/内存/打包认证。没有运行G001对战，不能由PASS对手成绩推导对G001胜率或天梯名次。
