# S3T：联合排班与人员规模的因果拆分

日期：2026-09-04。结果运行前登记。

## 问题

S3S 的联合排班同时用于“需要雇多少人”的估计和“已有人员今天怎么走”的实际编排。它将 G003 A 集平均工资从 5,796 降到 3,437，却同时少了约 8,261 的销售收入。现有证据不能区分：

1. 联合排班本身安排不好；
2. 排班器估计自己更高效，于是减少雇工，导致生产、回仓或销售链后续断裂；
3. 两者存在交互。

本轮不修改固定人数、产业目标、出售阈值或任何对手条件，只把同一个联合排班能力按使用位置拆成两个独立开关。

## 2×2 配置

| 配置 | 实际路线编排使用联合排班 | 雇工数量估计使用联合排班 |
|---|---:|---:|
| `old` | 否 | 否 |
| `compile_only` | 是 | 否 |
| `hire_only` | 否 | 是 |
| `compile_hire` | 是 | 是 |

S3S 的旧 `regret_schedule=true` 继续同时开启两处，作为兼容回归；S3T 使用新的独立开关。四组均关闭 `split_service_jobs`，避免把第三个因素混入本轮归因。若 `compile_only` 有稳定收益，再与任务拆分做下一轮有因果依据的组合，而不是直接扩大所有开关的笛卡尔积。

## 验证与判定

- 机制测试必须证明两个开关只进入各自上下文；S3S 旧开关语义不变。
- 关闭两个新开关时，旧版完整对局逐局一致。
- `compile_hire` 必须与 S3S `regret_only` 在同 seed、同座位逐局一致。
- 本轮使用 A=20261401–20261450、B=20261501–20261550，PASS 加原八对手，四配置、双座位，共 7,200 局。这些均是开发集。
- 报告胜率、我方现金、分差、工资、雇工人日、销量、日末损失和运行速度。按 seed 合并座位估计交互；任务减少或路线成本下降不能替代终局现金和胜率。
- 若出现多对手一致、PASS 不明显退化的候选，先冻结参数，再使用新的 J=20262301–20262350 完整复验。J 一旦使用即归开发集。最终验收 seed 不动。
- 不因单批、单对手或单项结果删除能力；也不因某个组合有效就宣称达成最终 90% 目标。

本轮不输入隐藏信息、真实未来、身份或 Replay，不修改官方 1.32.7，也不提交、不训练、不推 Git。
