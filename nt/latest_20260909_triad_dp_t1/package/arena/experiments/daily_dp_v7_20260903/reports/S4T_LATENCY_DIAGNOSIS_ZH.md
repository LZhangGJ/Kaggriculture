# S4T 1.87秒单步：初步性能诊断

2026-09-04。用户追问C++单步1.87秒是否实现有问题。结论：**存在明显的组合性能问题；当前证据定位到决策评估的嵌套计算，尚不是规则状态错误或无限递归的证据。不能把这当成多人协作天然需要的成本。**

## 实测，非猜测

- 初始20场探针：原两控制单步最大约3.5ms；工人全开/关联全开约189ms；完整自主组合约1.870s。
- 额外8场完整真实G003对局，仅加外部计时和计数器读取，未改任何决策参数或运行源码。
- seed 20262702、step 211（日索引8、日内19）两个座位分别约1.849/1.863秒，CPU时间约1.870/1.890秒。不是单次系统等待。WSL的计时源/并行官方检查可能使CPU与墙钟有小差异，不改变主要判断。
- 此步只有一次 `day_value.checks` 增加和一次共享插入。真实控制器的portfolio计数不增加；昂贵项目比较发生在被复制的条件预测控制器中，不能只凭外层计数认为没有计算项目。
- 另一seed最慢发生在step216日初，约0.65秒，真实上层生成201个粗候选、精评18个。说明日初投资比较本身也有成本，并非全由共享接手函数造成。
- 计时是 `Controller.act`，不是规则引擎 `env.step`，不是所有719步都花1.87秒，也不是最终Python提交的时延验收。

## 源码对应的计算放大

`dayvalue::accept` 比较KEEP与新排程，分别调用 `schedule_value`；各自推进当前日并重新规划下一日。打开联合投资后，下一日又会进入 `compare_portfolios`，对多个项目组合评估未来工资。

`portfolio::future_wages` 对未来每一天构造任务，再从0至max_hands逐个尝试人员数；每次 `pack` 在regret开关全开时再做一遍较昂贵的插入排程。末尾 `residual/wages_on` 还会估算剩余日期工资。

也就是：两套人员安排 × 下一日项目组合 × 剩余日期 × 试探雇工人数 × 人员排程。这是已确认的调用结构；各函数的精确百分比仍需函数级profile，不能杜撰占比。

代码中条件预测明确关闭 `day_consequence_compare`，故目前没有发现此估值函数无限自递归。官方状态/原始对手动作验证正在顺序完成；一致性通过也不能证明经济选择正确。

## 处理边界

继续冻结全开配置做离线强度诊断，不晋级、不提交；不靠关闭多人协作来掩盖性能问题。若继续优化，优先复用相同任务集/同等未来日的工资排程、相同日历和估值中间结果，明确评估层的共享上下文。缓存键必须涵盖会影响排程的状态/参数，先逐步动作及终局一致，再衡量速度。未实施优化前，不承诺1秒内。

证据：`receipts/s4t_runtime_probe_v1/acceptance.json`、`receipts/s4t_action_cost_trace_v1/acceptance.json`；工具 `tools/trace_s4t_cost.py`。本诊断没有新策略、Oracle或单seed参数调整。
