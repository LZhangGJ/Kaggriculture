# R2 P16：采购异常后的日内恢复

**2026-09-11 交接更新：** 新增两份真实提交、25 种子测试后，本版为 69/100 胜，完整工作链版为 74/100 胜；不支持直接替换工作链版或宣称本地最强。开发原理、最新结果及运行方式见 [仓库 agent.md §12](../../agent.md#r2p16-route-agents)，证据见 [交付记录](../../evidence/r2p16_route_agents_20260911/README_ZH.md)。下文的“验证状态”是此前 252 局记录，不覆盖这轮新增面板；其中工作区路径为历史来源。

本包在完整任务链版本上增加了 C++ 恢复决策。每日经营方向仍由现有规划器生成；执行器每一步核对真实现金、库存、种子和雇工，遇到采购缺口时重新安排当天剩余工作。这是决策逻辑修改，没有重新训练模型。

默认入口 `main.py` 加载 `build/revision3/route3.so`。旧的比赛基线及完整任务链版本保留在各自目录中。

**实际行为**

1. 买种子、饲料、动物、土地或雇工未足额成交，或者实际现金低于预计且无法支付后续订单时，启动恢复。
2. 撤下剩余的旧采购队列，重新读取当前工人位置、背包、仓库、种子和剩余小时。已经做完的工作通过真实盘面和完成记录保留。
3. 计算实际缺货量。背包中的物资属于具体工人，路线验证必须证明它能够用于所分配的工作。
4. 从零新增雇工开始试排，按今天已经雇过的人数计算下一名工人的真实工资。只有能在日终前完成整个工作计划的方案，才允许发出相应采购和雇工订单。
5. 若必须卖货筹资，先卖仓库中未被任务和饲料储备占用的现货，下一步根据真实到账金额再次计算。未卖出的商品、未来收获和工人背包都不算可支出现金。
6. 资金或时间仍不足时，按现有任务价值估计逐步延期未开工的投资；保留现有资产的维护与收获。延期重种不会提前铲掉现有多年生作物。
7. 成交后重新验证路线，再交回现有逐步执行器。原承诺不因延期而删除，未完成任务仍由原审计口径计入。

恢复使用原有排班器、完整动作链修复和观察盘面模拟器。播种及养殖建设保留动作先后关系；现有资产的收获、喂养和照料仍可由不同工人分担。代码不接收比赛 seed、对手身份、隐藏库存或未来 replay。

**实现位置**

| 文件 | 作用 |
|---|---|
| `policy/route_recovery.hpp` | 缺货计算、筹资、追加人手、项目延期、当前状态下的路线验证与安装 |
| `policy/route_economics.hpp` | 保存一步预期并与下步真实成交结果对账 |
| `policy/triad.hpp` | 在执行旧指令前接入恢复流程 |
| `policy/executor/policy.hpp` | 仅对恢复流程延期的重种项目保护原有作物 |
| `policy/search.hpp` | 调试统计；外层经营预测不递归启动恢复搜索 |
| `policy/bridge.cpp` | 提供原承诺和延期任务的只读审计接口 |
| `tests/test_route_recovery.cpp` | 采购恢复及边界检查，包含原有测试 |

调试统计中的 `recovery_events` 是恢复事件数，`recovery_checks` 是恢复决策步数，`recovery_sales` 是分步筹资次数，`recovery_orders` 是补购/追加雇工批次，`recovery_installs` 是恢复路线安装次数，`recovery_deferred` 是延期的字段动作数量。延期不是完成；`td_route_required` 保留原承诺，`td_route_deferred` 可读取单独的延期记录。

97 项检查通过：20 项经济与容量检查、58 项完整任务链检查、19 项恢复检查。

32 局回归已通过完整 replay 核验。14 组没有采购异常的对局，新旧版全部 719 步动作一致。另 2 组是已知采购不足种子的换座测试：首次变化均在第 241 步，此前双方观察完全一致；旧版每局漏 4 个动作，恢复版漏 0 个动作。

在该种子的第十一天，恢复版先卖 2 单位羊毛和 1 单位肥料，真实现金从 36 增至 269；下一步补购 2 包甜瓜种子，并追加 4 名雇工，连同已雇的 4 人共 8 人。旧版当天雇 7 人、工资 33；恢复版工资 54，多付 21，补齐两块田的播种和浇水。最终恢复版现金为 118710，对面的旧版为 106513。旧版互打的对照为双方 89068。后续双方均实时决策，因此终局差额包含生产和对手响应的连锁影响。

5 个新种子 × 11 个原始对手 × 两座位 × 两版本共 220 局，两版均 88 胜、22 负，平均终局现金 116957.94，平均工资 4058.98。110 组配对的全部 719 步动作一致，没有触发恢复；该集合验证正常路径兼容性，尚不证明普遍增胜。

最终共 252 局全部通过完整 replay 复核，双方 362880 份观察一致。所有对局使用此前编译并校准过的 C++ 裁判库，本次没有重写或重新编译对局裁判。完整指标及单步计时见 [验证报告](VALIDATION_ZH.md)。

**适用范围与代价**

该流程可在任意非终局 step 因成交异常触发；并不把每天的完整经营规划改成每步全量重算。候选路线必须通过已有模拟器验证，但所用排班搜索有边界，不保证找到全局最少雇工数。

筹资及采购步骤目前暂停工人路线，等待真实成交。恢复可能需要增加雇工；其目标是避免缺货让后续生产失效，不能保证每局都节省工资。若现有维护本身也无法全部完成，会保留原债务记录，交由已有服务恢复流程继续做可执行的工作。

本地验证不能替代比赛沙箱的时限测试。正常对局和异常触发的强度结果应分别解读，具体样本和计时见实验报告。

**运行与复现**

Linux/WSL 中直接加载本目录的 `main.py`。若重新编译，使用独立输出路径，构建脚本会拒绝覆盖已有二进制：

```bash
python3 build.py --out build/local_check/route3.so --unit
```

实验目录：`experiments/r2p16_route_recovery_20260910`。其中 `run.py` 复用已编译的原生对局宿主，`verify.py` 逐步核对完整 replay 和指标，`inspect.py` 检查第一次行为变化是否发生在真实恢复事件之后。`revision2` 是开发阶段候选，最终结果只使用 `revision3`；其源码快照保存在该构建目录下。
