# Candidate8 第0天/第1天公开状态策略验收报告

日期：2026-08-30  
结论：**工程闭环通过，策略效果不通过；不得继续扩展到第3天，也不得视为可提交策略。**

## 1. 本次验证的边界

本次验证只回答一个问题：

> 训练阶段用 C++ 模拟器将候选续跑到终局制作反事实标签后，模型能否在实战选择时只看第0天或第1天的公开盘面，选出优于 R6/KEEP 的候选？

它与此前全胜 G001 的 8 节点 Oracle 不同：

- 8 节点 Oracle 在每个决策点都知道随机事件和对手后续动作，并将候选直接模拟到终局后再选择，是不可部署的理论上限；
- 本次模型选择不读取 future outcome、对手编号、随机种子或未来动作；
- 训练标签可以使用终局续跑，但真正闭环评测时不允许看未来。

## 2. 实现与工程验收

### 2.1 修复的两个真实问题

1. 第0天候选提交后，第1天探针错误继承了 `candidate8_decisions` 和 `last_plan_step`，导致所有候选实际上重复第0天动作。旧数据已标记为 `INVALID`，未参与训练。
2. 当前计划目标可能低于已经发生的不可逆投入，导致第1天除 KEEP 外全部被错误过滤。现已使用真实不可逆承诺作为候选下限，并允许超出新动态上限的既有项目保持或缩减，但不允许继续扩张。

同时增加了候选签名重复的硬检查，防止类似问题再次静默产生无效数据。

## 4. 第1天反事实标签与模型

第1天正式标签库的 Oracle 显示候选空间有价值：

- 66.18%的局面存在能改善胜负的候选；
- 81.25%的局面存在能改善分差的候选。

这说明问题不是“候选中完全没有好动作”，而是“公开状态模型能否稳定选对”。

使用 LightGBM LambdaRank，按对手和随机种子同时隔离。模型输入只有：

- 当前公开状态；
- 候选参数和候选家族；
- 公开座位信息。

模型不使用对手编号、随机种子和终局标签作为输入。

最严格的联合未见切分结果：

- 激活率：75.00%；
- 精确 Oracle 召回：0%；
- Oracle recall@8：15.63%；
- 相对 KEEP 胜率：-0.78个百分点；
- 平均分差：-1,386.24；
- 平均现金：-1,360.30；
- 负效用率：56.25%。

五项既定门槛全部失败。

## 6. 为什么 Oracle 很强，模型仍然失败

核心不是执行器，而是当前标签和状态的可预测性不足：

1. 8个未来样本仍不稳定。把8个未来拆成两组4个，候选效用相关系数只有0.149；两组精确最佳候选一致率只有4.60%，top-8互相覆盖仅19.67%。
2. 第1天尚早，很多随机事件尚未发生；相同公开盘面在不同未来剧本中的最佳选择可以完全相反。Oracle能看见这些未来，模型不能。
3. 当前模型过度激活：内部联合未见激活75%，独立盲测激活81.25%；安全阈值没有成功识别“应保持 KEEP”的局面。
4. 第0天固定动作本身没有通过真正盲测，导致第1天模型是在较差开局上继续选择。

因此，不能把失败简单归因于“模型参数不够”或“候选数量不够”。当前更直接的证据是：**训练目标含有大量不可由当时公开状态预测的未来噪声，而且没有可靠的保守退让机制。**

## 7. 验收决定与下一步

### 决定

- Candidate8 工程闭环：PASS；
- 第0天固定策略：FAIL；
- 第1天公开状态 LambdaRank：FAIL；
- 扩展到第3天及以后：STOP；
- 当前模型用于提交：禁止。

### 建议的下一轮最小实验

1. 第0天暂时恢复 R6/KEEP，不使用固定扩产动作。
2. 将第1天目标改为“跨更多未来剧本的稳健期望/CVaR”，而不是追逐单组未来中的 Oracle 排名；先验证32或64个 future 后标签是否稳定。
3. 只学习“候选相对 KEEP 的保守增益”，当置信度不足时强制 KEEP；先证明低激活率下不退化，再扩大动作覆盖。
4. 增加不同公开盘面的训练状态，而不是只增加同一状态的树模型参数。
5. 只有在完全独立对手和新种子上同时满足胜率不降、分差上升、零硬错误后，才允许进入第3天。
