## 2. 最重要结论

这版 Rank1 不是“每天从零规划”，也不是“从几条固定拳法中切换”。更像：

> 固定一个可靠的早期开局骨架，再根据商店、市场、现金和对手公开盘面，连续修改产业规模、投产日期、人员、土地、出售窗口和后续布局。

对 6 个阶段的 8 个产业购买量、雇工和土地进行聚类，最佳结果是 4 类，但轮廓系数只有 `0.133`。这表示这些局面并没有清楚分成四条离散路线，更多是连续、多维的参数变化。

因此我们的候选单位不应继续局限于：

```text
产业 A -2/-4  ->  产业 B +2/+4
```

而应升级成：

```text
新计划 = 当前计划 + 参数化计划修改 ΔP

ΔP = 产业数量向量
   + 生效日期
   + 每日雇工/土地容量
   + 出售窗口
   + 布局与人员配置
   + 偏差恢复方式
```

## 3. 当前规划器和 Rank1 的本质差距

当前无高手日历规划器不是完全没有扩产能力：基础边际分配器会逐个 `+1` 增加项目，并由解析公式决定停止。但进入 W3 反事实比较的局部组合候选仍是：

- 一个来源产业；
- 一个目标产业；
- 数量仅 `(2,2)、(2,4)、(4,2)、(4,4)`；
- 最多暴露 16 个排序后的候选；
- 单边 SCALE 被解析贪心提前决定，不能和其他宏观方案公平续跑比较。

所以当前的真正缺口不是“整数 1 无法表示”，而是：

> 单边扩产、停止、日期、土地、人员、出售和布局没有作为同级反事实候选交给高速模拟比较；解析公式在候选生成之前就替我们做掉了大量决定。

## 4. 应补入候选空间的高级能力

### 4.1 连续规模，而不是只用 2/4

77 局最终累计购买量呈连续分布：

| 产业 | 最小 | 中位数 | P90 | 最大 |
|---|---:|---:|---:|---:|
| 小麦 | 81 | 129 | 164.4 | 192 |
| 胡萝卜 | 0 | 29 | 76.6 | 89 |
| 番茄 | 0 | 0 | 23 | 29 |
| 草莓 | 9 | 28 | 38 | 58 |
| 甜瓜 | 12 | 16 | 18.4 | 21 |
| 鹅 | 0 | 0 | 4 | 13 |
| 牛 | 3 | 8 | 12 | 19 |
| 羊 | 2 | 8 | 15.8 | 19 |

每天的产业购买量也不是 2/4 离散档。小麦出现 1–26，胡萝卜 1–22 和 29，草莓 1–18，牛羊鹅出现 1/2/3/4。

应新增：

```text
SCALE_UP(project, integer_delta, effective_day)
SCALE_DOWN(project, integer_delta, effective_day)
STOP_NEW_INVESTMENT(project, effective_day)
```

实现时不应枚举所有整数笛卡尔积。先由经济与容量算出中心数量，再保留中心附近 `-2/-1/0/+1/+2`、产能断点和截止时间断点。

### 4.2 单边扩产/停止，不强制找一个交换来源

全体 2,310 个“局×天”中：

- 有 `1,141` 天只新增一个产业，而且全部发生在开局之后；
- 这说明“只加某产业”必须是独立候选，不能强制同时减少另一产业；
- 各产业最后一次购买日期变化很大，说明“停止继续投资”也是计划变量。

典型日期范围：

| 产业 | 首次购买日期 | 最后购买日期 |
|---|---|---|
| 牛 | 固定从第0天开始 | 第0–17天 |
| 羊 | 固定从第0天开始 | 第0–19天 |
| 鹅 | 第6–14天 | 第8–19天 |
| 甜瓜 | 固定从第0天开始 | 第6–19天 |
| 草莓 | 固定第2天开始 | 第6–13天 |
| 番茄 | 第16–17天 | 第17–18天 |
| 胡萝卜 | 第21–26天 | 第26–27天 |
| 小麦 | 固定第0天开始 | 第19–27天 |

当前只有“数量”而缺少“生效日”，会把收益不同的计划错误视为同一个候选。

### 4.3 多产业联合调整

直接轨迹证据：

- `280` 个局日同时新增至少 3 个产业；
- `168` 个市场帧同时调整人员/土地容量并购买至少 2 个产业；
- 77/77 的开局都在同一事务期内形成小麦、甜瓜、牛、羊四项目组合；
- 常见日级组合还包括“小麦+草莓+甜瓜+羊”“小麦+草莓+牛”“小麦+草莓+羊”。

应新增稀疏向量候选：

```text
REBALANCE(
  project_delta[8],        # 允许 1～4 个非零项目
  worker_target_by_day,
  land_delta,
  effective_day
)
```

这不等于一次枚举 8 维所有组合。可以先生成单项目边际，再用 beam search 只组合互补的前若干项目，并对单项目、多项目、扩地和收缩分别保留配额。

### 4.4 投产日期、雇工曲线和土地必须成为联合候选

Rank1 的日雇工目标不是一个常数：

- 第0天固定 4 人；
- 第1天为 2–3 人；
- 第6天升到 8 人；
- 第7–10天在 6–12 人之间继续爬升；
- 第11天后通常为 12 人。

土地则基本表现为：第5天买第一块，第8天买第二块；3/77 延到第9天。土地变化没有雇工和产业数量那么自由，但至少证明“扩地日期”需要可调整，而不能只由一个固定容量阈值隐式决定。

应新增：

```text
CAPACITY_BUNDLE(
  project_delta,
  hand_target_curve,
  land_delta,
  effective_day,
  liquidity_reserve
)
```

### 4.5 根据商店/市场状态生成产业分支

使用不含作者、Episode ID、未来状态和对手私有库存的浅树，只预测后续宏观分支，得到以下交叉验证关联：

| 后续分支 | 较早检查点 | Balanced accuracy | 最强公开关联 |
|---|---:|---:|---|
| 第5–19天再扩至少6羊 | 第4天 | 0.499 | 尚不可预测 |
| 第5–19天再扩至少6羊 | 第9天 | 0.833 | `YARN_STORE` |
| 第5–19天再扩至少5牛 | 第4天 | 0.775 | 牛奶价格 |
| 第5–19天再扩至少5牛 | 第9天 | 0.781 | 牛奶价格 |
| 第15–24天启用番茄 | 第9天 | 0.786 | 番茄市场库存、披萨店 |
| 第15–24天启用番茄 | 第14天 | 0.823 | 番茄市场库存 |
| 第20–29天大胡萝卜后缀 | 第14天 | 0.767 | `PET_CAFE` |
| 第20–29天大胡萝卜后缀 | 第19天 | 0.817 | `PET_CAFE` |

这不是对源代码触发条件的证明，但已足以说明：候选生成器必须在商店和市场信息出现后主动提出牛、羊、鹅、番茄、胡萝卜等分支，而不是只给固定基础路线做 2/4 换仓。

值得注意：本次浅树中最强信号主要是商店、价格和市场库存；对手现金、对手牛羊数量属于次级信号。暂时没有证据支持按对手身份特调。

### 4.6 出售、持有和融资事务必须整体生成

直接观察到：

- `3,482` 个市场帧同时包含 SELL 和投资动作；
- 单帧实际使用到官方上限 10 个市场槽；
- 存在“卖牛奶→买地”“卖羊毛→买小麦→买牛”“卖草莓→买羊→买甜瓜种子”等链条；
- 多种商品在有可见库存时仍会跨日持有，并非一有货就全部卖出。

因此候选不能只输出独立的 `SELL_NOW` 标签，而应输出：

```text
MARKET_BUNDLE(
  sell_now / hold / partial_sell,
  sell_quantity_or_fraction,
  buy_sequence,
  financing_dependency,
  execute_window
)
```

事务编译器负责把“卖货融资”放到正确索引，模型只选择经济意图。

### 4.7 布局不是固定坐标，但也不是完全随机

第0天布局几乎固定：甜瓜、牛、羊的跨局 Jaccard 均为 1；牛羊靠近起始物流中心，作物更靠外。

到第9天以后布局开始明显分叉：

- 小麦 73 种布局；
- 草莓 69 种布局；
- 牛 32 种布局；
- 羊 31 种布局。

到第14–29天的作物布局跨局重合度很低。杂草、不同产业规模和任务兑现都会造成差异，所以不能把这种变化全部解释为主动最优布局；但它至少否定了“把高手坐标固定播放”的方案。

候选应使用布局配置而非坐标表：

```text
LAYOUT_PROFILE =
  animal_near_hub
  crop_outer_ring
  compact_same_project
  reserve_future_structure_cells
  worker_region_ownership
  weed_aware_relocate
```

执行器再根据当前真实空地、杂草和人员位置选择具体坐标。

### 4.8 人员必须执行联合任务图

77/77 局都出现同一帧至少 3 类生产动作并行；总计 `26,118` 帧。例如同回合同时：

- 建牧场、放动物、种植、浇水；
- 喂养、施肥、种植、浇水；
- 收获、种植、浇水。

所以候选价值不能只算“产业数量收益”。每个候选必须同步估计：

- 当天需要多少单位动作；
- 多单位能否并行完成；
- 是否跨越地块与人员容量断点；
- 事务融资后能否及时落地。

这部分不要求模型输出每一步移动，而是要求候选携带 `LABOR_PROFILE` 和任务优先级，交给联合调度器执行。

### 4.9 偏差恢复要允许延迟或放弃

77 局可见 `3,815` 次杂草出现/消失过程：

- 可见持续时间中位数 21 帧；
- P90 为 64 帧；
- 最长 288 帧；
- 终局仍可见杂草平均 2.51 个。

这说明强 Agent 并不是“杂草出现就立即清除”。远处、低价值、不会阻塞关键布局的杂草可以延迟，甚至留到终局。

应新增：

```text
RECOVERY(affected_project, REPAIR_NOW / DEFER / IGNORE, deadline, value_loss)
```

真正的硬错误仍必须马上修；经济性偏差应由机会成本决定。

## 5. 推荐的新候选语法

第一版建议统一为：

```text
PlanEdit:
  mode:
    KEEP
    SCALE_UP
    SCALE_DOWN
    STOP_NEW_INVESTMENT
    REBALANCE
    CAPACITY_BUNDLE
    MARKET_BUNDLE
    LAYOUT_PROFILE_EDIT
    RECOVERY

  project_delta[8]: sparse integer vector
  effective_day: now / +1 / +2 / next_event / latest_profitable_day
  hand_target_delta_by_day
  land_delta
  sell_policy
  layout_profile
  replan_scope
```

在线不应穷举所有字段组合。正确漏斗是：

1. 硬合法性、不可逆承诺和截止时间先过滤；
2. 每类候选分别生成，保证单边扩产、多产业、日期、容量、市场各有名额；
3. 解析价值器只淘汰明显差的，不再把所有候选按同一个分数截成 Top8；
4. C++ 离线反事实续跑提供真实标签；
5. 线上 Python 只用轻量排序器从少量候选中选择，不能在线跑大量终局模拟。

## 6. 实现优先级

### P0：先扩大真正的项目选择空间

1. 把单边 `SCALE_UP/SCALE_DOWN/STOP` 暴露为反事实候选；
2. 数量从固定 2/4 改为整数中心邻域和产能断点；
3. 支持最多 4 个产业非零的稀疏 `REBALANCE`；
4. 加入 `effective_day`；
5. 把雇工和土地作为同一个容量包一起比较。

### P1：补市场和执行能力

6. `SELL_NOW/HOLD/PARTIAL` 与融资购买组成有序事务；
7. 布局配置与人员区域配置成为候选参数；
8. 杂草、部分成交和任务延期进入局部恢复候选。

### P2：再训练排序器或宏观 Self-play

候选语法未补全前，模型只能在狭窄候选中学得更准确，无法产生 Rank1 这类连续调整能力。补全后再让 C++ Oracle 对同一局面比较候选，用终局胜负、分差和执行失败率产生排序标签。

## 7. 验收建议

新候选器至少要通过：

1. 不使用 Crop Dusta、Submission ID、Replay ID 或固定坐标；
2. 能表达 77 局出现过的单项目追加量、最多四项目联合调整和日期范围；
3. 能表达 10 槽有序融资事务；
4. 对商店/市场变化能同时生成 KEEP、扩产、延迟、转产和市场候选；
5. 每类候选有独立保留配额，避免旧解析分数把新类别在 Top8 之前全部删掉；
6. 用当前 77 局做覆盖测试，用其他 Rank1/金牌 Replay 做留源验证；
7. 最终效果仍以 C++ 独立事件库、多对手、双座位和官方 Python 1.32.7 复验为准。

## 8. 实事求是的边界

- 可以确认：Rank1 的实际动作呈连续规模、多项目联合、日期变化、有序融资、动态布局和延迟恢复。
- 高可信关联：羊与 YARN 商店、牛与牛奶市场、番茄与番茄库存、胡萝卜与 PET_CAFE。
- 不能确认：这些就是源代码里的真实 if 条件；浅树只能说明公开状态与后续分支有关。
- 不能确认：四个聚类就是四条内部拳法。低轮廓系数反而说明更可能是连续调参。
- 不能直接从这 77 局证明某个候选必然提高我方胜率；必须进入同 seed、双座位、多对手反事实验证。

最终判断：这批 Replay 对候选空间扩展非常有价值。最值得迁移的不是固定日历，而是“参数化计划修改 `ΔP`”这一层决策自由度。
