# C++ Clean133：实际胜率与 Candidate8 Oracle 上限验收

日期：2026-08-30（JST）

## 1. 结论

当前可部署的 R6 规划器，对 133 条通过硬错误筛选的 C++ 固定路线代表，实际总胜率只有 **20.58%**。同一规划器若在每个重规划点知道该局真实未来，并从现有 Candidate8 候选中挑选最有利方案，经验上限为 **76.64%**。

这说明存在很大的选择/估值缺口，但不能得出“只训练选择器就能全对手 90%”的结论：

- 只有 1/133 条路线的当前实际胜率达到 90%；
- 44/133 条路线的 Oracle 达到 90%；
- 73/133 条路线的 Oracle 位于 50%–90%；
- **16/133 条路线即使 Oracle 也低于 50%**。

因此目前同时存在两类问题：

1. 很多局面中，候选里已经有好答案，但当前规划器选不出来；
2. 面对至少 16 条路线，现有候选表达、执行能力或跨阶段组合搜索本身仍不够。

## 2. 口径

### 2.1 C++ 对手范围

路线库共有 178 条选中路线：

- 133 条 `source_execution_hard_failures == 0`，本次全部纳入；
- 42 条原始执行存在 1 个或更多硬失败，本次排除；
- 3 条为 `oracle_only` Replay tape，本次排除。

这里的 133 个对手是 **C++ 固定路线代表**，不是“68 个跨 Python/JAX/C++ 运行时 Agent 已全部精确 C++ 化”。本轮适合高速筛选经营结构和市场响应，不替代以后对完整动态 Agent 的最终复验。

### 2.2 实际胜率

- Agent：当前可部署 R6；
- 不读取未来随机事件；
- 每个对手 32 个全新种子 × 双座位 = 64 局；
- 合计 8,512 局；
- 16 个 CPU worker。

### 2.3 理论上限

本报告所称“理论上限”是 **当前 Candidate8 + R6 执行器的经验上限**：

- 在第 3、6、9、12、15、18、21、24、27 天滚动重规划；
- 每次从当前完整可行 Candidate8 候选池中选择；
- 每个候选从真实当前状态续跑到终局；
- 选择时直接使用该局真实未来；
- 优先级为胜负 → 分差 → 我方现金；
- 每个对手 8 个全新种子 × 双座位 = 16 局；
- 合计 2,128 个对局状态，完成 547,410 次终局续跑。

它不可上线，也不是整个游戏的数学全局上限：它仍受当前候选语法、R6 执行器、三天一次决策以及滚动贪心选择约束。

| 分层 | 路线数 | 含义 |

| 当前实际已 ≥90%，Oracle 也 ≥90% | 1 | 当前规划器已能稳定处理 |

这比只看总胜率更有用。后续应优先把 43 条“Oracle 已 ≥90%”路线用于训练选择器；把 16 条“Oracle <50%”路线用于创造新的市场博弈和经营响应候选。

## 7. 性能与工程验收

- 实际 Arena：8,512 局，20.73 秒，约 **410.6 完整局/秒**；
- Oracle：547,410 次终局续跑，纯模拟 1,525.84 秒，约 **358.8 次终局续跑/秒**；
- 133/133 对手均有实际和 Oracle 回执；
- 缺失、额外和重复对手 ID 均为 0；
- 两组均无可避免作物损失、动物损失和终局容量溢出。

## 8. 下一步建议

先不要把全部问题交给 RL 或 LGBM。

1. 对 43 条“Oracle ≥90%、实际 <90%”路线，生成状态—候选—真实胜负/分差标签，训练可部署选择器；
2. 对 16 条“Oracle <50%”路线，先增加有证据的市场候选：精确抢卖比例、延迟出售、卖货融资后购买、未来出售债务回写；
3. 若补市场候选后仍明显为负，再扩完整经营结构和跨阶段候选序列；
4. 所有修改继续用 32 种子、双座位实际组与 8 种子、双座位 Oracle 组复验，禁止只看 2×2 快筛。
