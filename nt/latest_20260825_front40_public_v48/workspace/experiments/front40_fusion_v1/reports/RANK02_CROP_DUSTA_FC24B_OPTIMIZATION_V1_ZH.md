# Rank02 Crop Dusta 家族对 FC24B 优化报告 V1

## 1. 结论

Crop Dusta 家族已经完成一轮从 Replay 路线库、静态路线选择、LGBM 路由、两阶段路由、兼容切换、逐步动作合成到跨家族混合的系统优化。

- 当前可复现的纯 Crop Dusta 最佳版是 `rank02_crop_dusta_robust_all3_stable_v29`。
- 在此前完全未参与选择的独立随机库 `seed=248001..248256`、双座位共 512 局中，胜 FC24B **227/512 = 44.34%**，平均分差 **-3,176**。
- 512 局全部完成 719 步，`hard_counter_total=0`，但平均每局仍有 30.54 个 Replay 意图因实时状态不匹配而被安全跳过或重同步。
- 该家族没有达到入选门槛 `>50%`，不能伪装成成功拳法；但已保存为历史最优失败家族，后续可作为融合时的作物路线组件。

这里的 `50%` 只是进入强拳候选库的最低线，不是优化停止线。对任何达到 50% 的后续家族，仍要继续提升到多个独立留出库不再出现稳定增益，再切换下一位高手。

## 4. 为什么“路线库有能力”但路由器学不会

在已知终局结果后，从 97 条完整路线中为每个局面挑最好的路线，反事实 oracle 在多个面板可达到约 **86%–93%**。这说明路线库中确实存在很多能击败 FC24B 的完整经营链。

但运行时看不到未来商店、未来市场扰动和后续杂草。第一家商店出现时的公开状态不足以稳定判断哪条 719 步路线最终最好。于是：

1. oracle 使用了未来结果，只代表路线库容量，不代表可部署能力；
2. LGBM 在训练面板记住了局面和路线收益的偶然关系，换随机库后不能稳定泛化；
3. 到第 144 步再切换完整路线时，旧路线已经形成动物、作物、单位位置和库存承诺，新路线默认的前置状态不成立；
4. 逐步投票或跨家族拼接会把完整任务链拆碎，虽能安全 no-op，却不能形成高收益经营闭环。

## 5. 平台期判断

本轮不是因为刚到某个数字就停止，而是已经验证了四类互不相同的提升路径：

- 扩大与压缩路线库；
- 静态、LGBM 和两阶段动态路由；
- 只在兼容商店上下文中切换；
- 逐步动作合成与跨家族接管。

结果表明，继续围绕“从静态 Replay 中选择或拼接动作”加补丁，不能可靠越过 50%。主要缺口不是 JAX 规则执行，而是缺少 Crop Dusta 原 Agent 的在线经营状态和偏差恢复逻辑。若没有新的源代码、更多能揭示状态条件的 Replay，或一套可维持任务承诺的语义级动态控制器，同类优化的预期收益已经很低。

因此冻结 V29，转入下一个行为不同的前排家族；这不是放弃整体目标，而是避免在证据已显示的平台期继续消耗计算。
