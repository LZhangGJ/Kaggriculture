# T2-R2 BatchedDelivery：交付动作与共享仓容修复

日期：2026-09-09。基线：已修复且经用户本地确认的 T2-R1 ServiceAligned。

## 1. 结论与版本身份

本轮交付的是 **合并卸货＋同一步仓容预留** 的小修复，不是改变产业配方、经营候选数量、动物维护 DP 或竞争参数的新策略。

- 默认 `batch_delivery=1`，其余经营参数与 R1 一致，特别是 `service_reconcile=2`。
- `live_ledger=0`；日内实时估值账本实验未通过胜局回归，没有并入交付策略源码。
- 交付二进制 SHA256：`877f196113692722edc8a5b3e30d2d3dd1d4700b0772c13f1e3f2ad7a9ac0ef2`。
- 已从整理后的交付源码再次编译，得到同一 SHA256，并通过发布行为检查。
- Python/C++ 设置参数从 R1 的 37 项变成 **38 项**；应成套使用 `policy/`，不能只更换 `.so`。

**已修复定点败局，但新增小面板总胜率持平，不宣称整体胜率提高。**

## 2. 修复机制

### 2.1 同一工人可以一次卸下全部无任务承诺的货物

R1 的 `early_deposit_action()` 在仓库位置主要通过 `PLACE(item, quantity)` 每回合卸一种商品。持有多种可售商品的工人需要多回合才能卸完。新的路径仅在以下条件同时满足时使用一次 `DROP`：

1. 工人已位于仓库位置，原有时间余量条件成立；
2. 持有的每一种商品都没有被该工人的剩余 FEED/FERTILIZE 任务占用；
3. 背包没有尚未安置的动物；
4. 剩余共享仓容足够容纳整包。

不满足条件时仍走旧的按商品部分卸货。终局日保留原有终局调度，不改变其收售边界。

这节省的是可避免的卸货动作，原任务路线和维护承诺没有被删除。仍由当前 observation 确认库存与位置。

### 2.2 同一步的后续工人必须看见已经占用的仓容

合并卸货后，将整个背包数量计入当步 `drop_qty`，后面的工人只能使用剩余容量；也将本次交付计入相应的交付销售账本。不能让两个工人各自认为同一段仓容仍然空闲。

市场端沿用 R1 的我方单位阶段投影和 `settle_market()`。货物真正进入仓库后才能参与当前步销售；既有饲料、肥料预留仍保留。没有读取对手私仓、真实种子、未来商店或对手 ID。

主要改动：`policy/executor/policy.hpp`、`policy/triad.hpp`、`policy/agent.py`、`policy/config.json`。差异见 `T2_R1_to_R2.patch`。

## 5. 未并入的实时账本实验

发现 R1 的日内追加投资仍使用早晨 `portfolio`，因此实验了从真实库存、现有生产和已付款未启动目标重建估值账本。

但它与合并卸货组合后，在 `2609096000/Three-Day` 的双座位原胜局中分别退步到 −1,039 和 −523。该实验虽能救回 G003 的重点案例，却不符合保住原胜局的要求。

因此交付 `policy/` 已删除该实验实现；`live_ledger` 保持 R1 的未启用占位设置。实验代码、配置、结果保留在 `evidence_r2/development_candidate_source.zip`、`live_ledger_rejected.patch` 和对应日志中。不能把组合版的 G003 胜局算给本次默认版本。

## 6. 正确性与重编译验收

- **16 项定向单元检查通过**：混合货物一次卸货、容量不足回退、零容量、保留饲料/肥料、未安置动物保护、终局边界、关闭开关、多人共享仓容，以及物品守恒。
- 最终二进制的 8 条完整轨迹在随包官方 Python 规则下重新产生动作，**5,752 步一致，最终双方现金一致**。
- 同 8 场实时轨迹中，随包审计器未记录到单位无效果动作；这不是对 224 场全部动作或所有状态空间的形式证明。
- 关闭 `batch_delivery` 后，对 R1 的 5 条既有完整轨迹进行 **3,595 步**比较，动作与现金全部一致。
- GCC 14.2 对整理后的源码重编译，重新得到上述同一二进制 SHA256；发布检查通过后才替换 `policy/agent.so`。
- 保留此前 `animal_path` 的 `noipa` / `noinline` 局部规避；本轮没有重新进行 GCC13、Clang 编译器矩阵测试。
- 八条构建回归使用冻结的双方动作做规则推进，属于编译/导出一致性检查；与 224 局实时对战是两类不同证据，不相加制造样本量。
- `build_policy.py` 已切换为本版八条黄金轨迹，不拿旧 R1 轨迹强行要求新行为不变。校验失败不会覆盖已有库。

## 7. 本地使用

Linux / WSL2，进入解压目录。文件校验不编译、不运行对战：

```bash
python3 verify_package.py
```

只重编译我方策略并执行八条构建回归：

```bash
python3 build_policy.py --cxx g++
```

Python 版本与随包运行器 ABI 不同，或需要从源码构建所有组件：

```bash
python3 -m pip install -r requirements.txt
python3 build_all.py --jobs 2 --cxx g++
```

构建不会自动启动 224 或 1,400 局。可另跑 16 项定向检查：

```bash
python3 test_correctness.py --cxx g++
```

每对手 32 局：

```bash
python3 run.py --tag r2_local224 --start 2609098000 --count 16 --threads 4
python3 run.py --tag r1_local224 --baseline --start 2609098000 --count 16 --threads 4
python3 compare_panel.py --results runs/r2_local224/rows.json
```

`--baseline` 明确指 R1，不是 T1 或原 T2。主 runner 限制 `--count` 为 1–16，防止误启动大面板；`--count 1` 是七对手双座位，共 14 局。新输出目录必须不存在。

线上入口仍为 `policy/agent.py::agent`。同一进程多局可使用独立 `Agent` 上下文。不应只复制动态库而沿用 37 参数旧包装器。未验证 Kaggle 线上排名及所有平台运行限制。

## 8. 接续边界

剩余工作仍包括投资估值与真实交付时间的统一、对手上市时序、现有维护与新投资的联合反馈。当前证据不能把 G003 的剩余差额唯一归因于其中一项。下一轮应把本面板标为已见回归数据，不再声称它是新的独立验收。
