# Kaggriculture：将五个公开方案迁移为 JAX 通用规划能力的 Codex 观点

日期：2026-08-19  
文档性质：**设计审查 / 尚未实施（DESIGN_ONLY / NOT_RUN）**  
目标：请 GPT 复核该迁移方向是否能够扩展本地规划器的高收益路线表达能力，同时避免把公开方案改写成另一套固定规则。

## 1. 当前背景

目前已经取得并冻结五个高潜力公开方案：

1. Boatlee V20；
2. Ray K320；
3. Tetsutani Adaptive Premium Queue；
4. Kaito V27 Midgame Reset；
5. Flex V59 Multi-route。

这五个 Python Agent 已经精确迁移到 JAX。现有验收覆盖：

- 官方 `kaggle-environments 1.32.7`；
- 五个方案、两个随机种子、双方座位；
- 双方都会行动的镜像对局；
- 每个单位动作、市场订单、公开/私有状态以及终局奖励逐步一致；
- 20 局、每局 719 步，共 14,380 个决策步全部通过；
- RTX 3090、2048 batch 下约为 18.4 万至 25.8 万 transitions/s。

因此，这五个方案现在既可以作为 GPU 冻结对手，也可以作为规划能力审计的可执行证据。

但必须强调：五个方案之间存在大量共享路线和代码，不能把它们视为五种完全独立的策略思想。

## 2. 核心判断

我的结论是：**可以利用五个源代码补全我们的规划能力，而且很可能能够解决当前规划器约十万元收益的表达上限；但需要补的是“规划器”，不是官方规则模拟器。**

必须严格区分：

### 2.1 官方/JAX规则模拟器

职责是按照官方规则执行原子动作、市场结算、随机事件和状态转移。

这一层只能以官方 1.32.7 为准，不能因为公开 Agent 使用某种经验公式，就修改游戏规则。比如公开 Agent 内部曾使用旧价格公式排列卖单，这个行为可以在“对手复现控制器”中保留，但绝不能写进官方状态转移规则。

### 2.2 我们的JAX规划器

职责是决定：

- 做哪些经营项目；
- 投资多少；
- 何时开始和结束；
- 使用哪些地块；
- 工人如何分工；
- 生产、维护、收获、入仓和出售如何衔接；
- 市场、商店、随机事件或对手造成偏差后如何调整。

当前真正的限制在这一层：模拟器能执行高收益原始动作，但规划器还不能自主表达和生成同等复杂度的路线。

## 3. 五个方案应该迁移成什么通用能力

| 来源 | 不应照抄的内容 | 应迁移的通用规划能力 |
|---|---|---|
| Boatlee V20 | 某商店出现后直接选择固定路线 | 根据商店、市场价格、对手供给和可兑现窗口，在多个产业计划间动态路由 |
| Ray K320 | 固定提前 1/2/4 步抢卖及固定偿还逻辑 | 带截止时间的任务抢占、暂停、资源预留和事后恢复 |
| Tetsutani | 固定商品和固定 premium queue 顺序 | 预测未来市场窗口，反推收获、入仓、移动和出售的最晚执行时间 |
| Kaito V27 | 固定中期节点或固定动作日历 | 当计划与真实状态偏离过大时，从当前状态重新编译剩余经营日历 |
| Flex V59 | 固定路线加特定杂草修复 | 最小干预恢复：仅重建受影响任务链，保持其他项目和工人计划不变 |

迁移目标不是复制五个 Agent 的牛羊数量、日期和阈值，而是把它们证明有效的能力改造成参数化算子。

## 4. 建议的规划器结构

建议维持三层结构，并在其上补充偏差控制。

### 4.1 第一层：经营项目与完整日历

一个项目至少表达：

```text
Project(
    product,
    target_quantity,
    start_day,
    expansion_schedule,
    service_until_day,
    capital_budget,
    layout_region,
    expected_sell_windows,
    failure_policy
)
```

搜索器可以修改：

- 作物和动物组合；
- 每种产品的数量范围；
- 买入、扩张和停止维护日期；
- 雇工、土地、饲料、肥料和现金预算；
- 布局区域；
- 出售窗口和清仓方式。

低维搜索参数应编译成完整 30 天计划，而不是直接独立搜索数百个日历值。

### 4.2 第二层：任务图与联合调度

每个经营项目自动展开为完整任务链。例如：

```text
买牛 → 建牧场 → 买饲料 → 分配工人 → 定期喂养
→ 收集牛奶 → 运回仓库 → 等待窗口 → 出售
```

调度器必须支持：

- 一名工人持有连续多任务链；
- 多名工人并行推进不同产业；
- deadline 和未来重复维护成本；
- 工人、地块、库存、仓库、现金和市场槽位的共享冲突；
- 任务粘性，避免无意义地每步切换；
- 必要时进行局部换人或局部重排。

### 4.3 第三层：同回合事务编译器

必须能够表达有顺序依赖的市场事务：

```text
先出售库存获得现金
→ 再购买动物/种子/饲料
→ 再雇工
→ 再建立后续承诺
```

事务编译器需要维护 projected cash、库存容量、订单槽位和成交失败后的剩余承诺，不能把每个市场动作当成彼此独立的选择。

### 4.4 第四层：偏差检测与局部重规划

每一步或关键节点计算：

```text
Deviation = ActualState - PlannedState
```

主要偏差包括：

- 部分成交导致少买资源；
- 对手集中出售导致价格或市场容量变化；
- 商店窗口和计划不同；
- 杂草阻塞路径；
- 产品晚收、晚入仓；
- 现金、库存或工人数低于计划；
- 某个项目已经无法在终局前回本。

规划器只允许调用少量通用恢复操作：

- 延迟任务；
- 缩减项目规模；
- 更换出售顺序；
- 临时抢占人员；
- 补回被抢占的任务；
- 切换剩余产业；
- 放弃无法回本的项目；
- 从真实状态重新编译剩余日历。

恢复的原则是最小干预，而不是每次偏差后推翻整套路线。

## 5. 如何从源代码提取能力，而不是复制规则

### 步骤A：分支审计

把每个源代码分支记录为：

```text
触发状态
→ 采取的动作
→ 想保护或增加的经济价值
→ 占用的资源
→ 截止时间
→ 失败后的恢复方式
```

### 步骤B：同局面反事实消融

利用现有精确 JAX Agent，在完全相同的随机事件和对手下比较：

1. 原始分支开启；
2. 关闭该分支；
3. 改变触发阈值；
4. 用通用规划算子替代该分支。

比较最终现金、胜率、未完成承诺和硬错误。只有跨多个种子与对手仍然稳定有价值的分支，才升级为规划能力。

这一步非常重要，因为公开源代码中的 `if` 可能是：

- 真正有用的经营规律；
- 只对某个公开环境有效的特调；
- 旧规则遗留；
- 不影响结果的冗余代码；
- 作者尚未清理的错误。

不能仅因高分方案包含某个分支，就默认它有正向因果价值。

### 步骤C：参数化

例如不能直接复制 Ray 的“提前两步抢卖”，而应形成：

```text
PremiumPreemption(
    lead_steps = 0..6,
    minimum_expected_gain,
    maximum_interruption_cost,
    repayment_mode,
    deadline_guard
)
```

这些参数进入 GPU 搜索空间，由结果决定具体取值。

### 步骤D：JAX固定形状实现

计划、任务、事务和恢复操作均使用固定容量数组及 mask：

- `RouteGenome[B, ...]`；
- `DailyPlan[B, 30, ...]`；
- `TaskGraph[B, K, ...]`；
- `CommitmentLedger[B, ...]`；
- `DeviationState[B, ...]`。

分支使用 `jnp.where`、`lax.cond` 或固定循环，禁止在 rollout 中逐环境调用 Python Agent。这样才能保留十万级 transitions/s。

## 6. 建议验收标准

### 6.1 表达能力验收

- 不读取五个方案的 719 步原始动作录像；
- 仅通过高层项目参数和通用规划算子生成路线；
- 五种方案中的有效动作组合均可表达；
- 不存在未知动作、事件截断或任务容量溢出；
- 能生成与五个参考方案经营结构相近的路线。

这里不强制逐动作完全相同，因为目标是表达等价经营能力，而不是复刻录像。

### 6.2 执行与收益验收

- 官方/JAX模拟语义继续保持一致；
- 719 步完成；
- 非法动作、重复资源预留、无原因静默 no-op 等硬错误为零；
- 在静止对手和固定事件下达到参考路线相近的收益；
- 受到商店、随机事件或市场扰动后不会因微小偏差整局崩溃。

### 6.3 自创能力验收

GPU搜索至少产生一条满足以下条件的新路线：

- 参数组合不等于五个公开方案；
- 产业结构、布局或时间安排存在实质区别；
- 官方 Python 1.32.7 能完整执行；
- 在固定多对手池中优于其父路线或填补现有路线的明显弱点。

只有通过这一门，才能证明我们迁移的是通用规划能力，而不是隐蔽复制公开路线。

## 7. 主要风险

1. **样本偏差**：五个方案高度相关，可能共同忽略某些作物或布局路线。
2. **搜索维度爆炸**：不能直接把每天每个数值都当独立变量，应使用项目模板、分段参数和编译器。
3. **错误抽象**：某个具体 `if` 不一定代表可泛化规律，必须先消融。
4. **规划器过度保守**：合法性和任务完整性不能变成终局资产必须清零等过严限制；最终现金仍是主目标。
5. **吞吐下降**：不要把五个 Python 规则树逐字翻译成大量串行判断，应合并状态特征和批量计算。
6. **错误修改规则层**：公开 Agent 的预测公式属于策略，不属于官方游戏规则。

## 8. 推荐的最小实施顺序

1. 建立五个方案的能力/分支矩阵；
2. 对动态分支做 JAX 同种子消融，筛掉无价值或特调分支；
3. 先实现完整日历、多任务链和市场事务顺序三项最大表达缺口；
4. 再实现 deadline 抢占、偿还和局部重规划；
5. 将五个方案重新表达为高层 genome，禁止读取原始动作录像；
6. 在静止对手下搜索参数和新组合；
7. 加入五个冻结 JAX 对手测试抗干扰能力；
8. 对入选路线使用官方 Python 1.32.7 复验。

## 9. Codex最终观点

五个公开方案最适合作为：

- 规划能力的证据；
- 分支消融的基线；
- 表达完整性的测试集；
- GPU对手池；
- 新路线的父代和扰动中心。

它们不应该成为：

- 新的官方规则来源；
- 五套逐字翻译的硬编码 Agent；
- 搜索空间的边界；
- 某个固定阈值必然正确的证据。

一句话总结：

> 把五个方案转化为规划器的语法、任务算子和恢复工具箱，把数量、日期、布局、产业组合和触发阈值交给 GPU 搜索；最终用新路线能否脱离五个原型并在官方裁判中取得更高收益来证明迁移成功。

## 10. 请GPT重点复核的问题

1. 上述四层规划结构是否仍缺少影响高收益路线表达的关键层？
2. 五个方案的思想映射是否存在错误归因或过度概括？
3. 如何以最低维度 genome 表达完整 30 天经营日历，而不重新形成搜索爆炸？
4. 哪些分支最值得首先做因果消融，哪些可以暂缓？
5. “不读取动作录像但能生成等价经营结构”的验收是否足以排除隐蔽照抄？
6. 自创路线的验收还需要增加哪些多样性或稳健性标准？
