## 2. 本阶段到底改了什么

所有功能为独立参数，不按G001身份、Replay编号或真实seed分支。

| 能力 | 实现内容 | 实测判断 |
| --- | --- | --- |
| 公开对手供给 | 从公开作物/动物及其成熟日历估计竞争供给，不读取隐藏库存 | 旧集分差明显改善，但单独仍0/10胜 |
| 短期出售判断 | 比较已知城镇需求与双方可见产出，决定当前库存是否提前出售 | 有改善，不能独立解决强度问题 |
| 更宽的初始投资组合 | 384个通用作物/动物组合，之后仍由当前状态逐日规划 | 小集最优7/10，换seed仅2/20，证实不能据此晋级 |
| 有限作物轮换 | 收获后重新比较下一种作物，不只补种原品种 | 有的PASS提高，对抗不稳定，默认不启用 |
| 我方饲料需求 | 修正“计算了未来饲料量但未进入新项目供需估值”的遗漏 | 局部改善有限，未成为优先配置必选项 |
| 分日期现金流估值 | 分开种子支出、饲料/肥料、产品产出，按日期估计价格 | 有小幅分差改善，没有证明显著提高胜率，保留实验开关 |
| 经济条件扩地 | 比较不扩地和新增一块土地所能支持的新项目价值，再扣土地成本 | 进入S3C03；不再依赖第9/12天硬门 |
| 收获时点与有限作物施肥 | 小麦2/3/4日、胡萝卜2/3日等合法范围；施肥按预计增产与机会成本判断 | 组合有改善，施肥并非普遍增益 |
| 精确当次收获投影 | 用当前实际产量和当次浇水增量，不把理想满产当实际所得 | 进入S3C03，含终局成熟检查 |
| 利用空闲时间入库 | 路过仓库或工作提前完成时，保留后续所需物资，优先PLACE余货；可接SELL | 开发集有增益，跨seed并非最佳配置，不强制打开 |
| 有效维护 | 保证不连续两天缺水，成长/施肥生产日仍浇水；省去无法再贡献产出的CARE | 进入S3C03；不等于删除维护分支 |
| 末批后立即补种 | 收完草莓/番茄末批后，允许清地并在期限内补种；没种子时不向空地发WATER | 表达能力和机制测试通过，但整局结果不稳定，默认关 |
| 竞争收益影响 | 估计新增供给对公开对手后续收益的影响，而不只看我方现金 | 没有足够稳健的增益证据，默认关 |

S3C03并不是把所有新开关叠起来：它使用公开供给/短期出售、经济扩地、精确有限作物投影和有效维护；没有打开分日期估值、有限作物轮换、早入库、末批立即补种和竞争影响奖励。配置以JSON为准。

其初始投资组合为2牛、1羊、2鹅、4小麦、6草莓；这是有限范围内筛选出的初始参数，不是完整高手动作表。此后数量、土地、工人和执行安排由可见状态生成。目前不能声称已实现“任意开局都强”，也没有验证对其他强对手的泛化。

## 3. 不隐瞒失败实验

### 开局小样本过拟合

`portfolio_255`旧5个seed双座位7/10胜，新10个seed双座位2/20胜。`portfolio_182`旧6/10胜，新1/20胜。全部保留，不删除失败seed。

### 能力补齐不等于赚钱增加

末批立即补种的直观逻辑成立，但不能据此宣称普遍提升。相同50个seed、相同其他配置：

| 配置 | PASS均值 | G001胜局 | G001我方现金 |
| --- | ---: | ---: | ---: |
| S3C03，不立即补种 | 177,100.73 | 36/100 | 103,429.68 |
| S3C03，允许立即补种 | 176,918.43 | 31/100 | 97,686.85 |
| S1基线，不立即补种 | 176,340.59 | 2/100 | 76,705.47 |
| S1基线，允许立即补种 | 178,446.04 | 0/100 | 74,171.54 |

这说明“提早再生产”会同时改变用钱、工人、供给和价格，不能只看多收了几份产品。尚未完成收入/成本分解，不能把败因擅自归结为某一种机制。该能力留在实验库，未晋级。

证据：`../receipts/s3_renewal_new50/results.json`。

## 4. C++与官方一致性

本地批量热循环完全为C++：v7决策、完整G001决策、规则结算、下一步。Python只加载一次资产、调用批次、记录结果；少量官方复验例外。

- 官方1.32.7规则文件、vendor规则引擎保持冻结。
- G001仍为原始完整175路线/决策树/动态切换执行器，不是单条固定G001录像。
- v7 View没有真实seed、对手私有库存或未来商店/杂草。
- 分日期供给是条件预测，不是已知未来。官方相同seed在不同动作下，也可能因为空地数量改变随机抽样消耗而出现不同后续杂草/商店，不假装所有对照共用完全不变的未来剧本。
- S3C03在20261401–20261404双座位8局，719步全部官方/C++状态一致；原Python G001与原生G001每步动作一致，包含真实动态切换局。
- S3各新分支另有逐步官方复验，见`receipts/s3_*_official/`。
- 默认S1路径也重新与Python候选参考逐步比较通过，原开发seed20260903得到62,381对116,097。
- 扩展原生机制夹具500项通过，覆盖合法收获年龄、施肥产量、省水不减产、商品与现金单位分离、30天产出日历、末批收获→清地→补种顺序、缺种子后取消无效WATER。

**重要区别：**新S3分支目前以C++为实现主体，其官方复验不是“新S3 Python翻译也已通过”。`agents/agent_v7.py`仍是S1/S2与部分早期S3功能的参考，不应直接拿它冒充本阶段原生优先候选提交。分日期实验的Python入口明确拒绝运行，避免默默执行旧逻辑。

证据：`../receipts/s3c03_official_new8/acceptance.json`、`../receipts/s3_default_python_regression/acceptance.json`、`../receipts/s3_native_mechanisms_extended/acceptance.json`。

## 5. 性能

S3C03，完整G001，16线程，5个seed双座位重复100次共1,000局：

- C++批量热循环：0.955秒，约1,048完整局/秒，约753,240 transitions/s。
- 719步/局，两边策略都在计时内。
- 不含首次加载G001资产和进程启动；完整命令另需数秒。
- 重复运行的相同seed/座位现金、对手现金、切换状态一致；这不是额外1,000个独立场景。
- 8局官方复验中的候选原生单步最大实测小于0.8毫秒；不是所有硬件/局面的最坏上界，也不代表尚未迁移的Python版本时延。

计时对应源码快照在`../receipts/s3c03_native_throughput_1000/`。之后增加默认关闭的补种开关；复跑所有7个冻结候选，700个G001结果的现金/胜负与该阶段此前结果逐项一致。
