# 给队友：Day0–28 搜索与宽候选恢复

## 1. 两层不能混淆

上层是“做什么、做多少”的经营计划，下层是根据真实位置、资源和到期义务安排工人。C3/F3 都带有上层和下层；近日 PPO 只是夹在两层之间每天改一个项目，不是全部上层决策能力。

同一个日节点可以定义一个包含多个调整的候选。搜索器最终选**一套相容的方案**，不是把几个独立最高分动作任意拼起来。买羊、种麦、用工会竞争同一份现金、地块、工时；分别算可行并不保证一起可行。

## 2. 旧宽池在哪里

已在同一 Git 分支：

- [旧 Daily DP 动态生成器](../latest_20260904_dynamic_generator_cross300/README_ZH.md)。
- [原宽池实现](../latest_20260904_dynamic_generator_cross300/engine/native/investment_candidates.hpp)。
- 更早的 [Candidate8 / width12 / MCTS](../latest_20260901_candidate8_width12_mcts/README_ZH.md) 是另一套框架，不要只因都叫“候选”就当成同一 ABI。

特别区分：真正 Candidate8 宽版的 [adaptive_candidates.cpp](../latest_20260901_candidate8_width12_mcts/workspace/agents/route_clustering_switch_agent/fast_kaggriculture/src/adaptive_candidates.cpp) 已经生成有限的两产业释放/再投资、共同扩产，以及三产业“一减两增”候选；另有规模、延期、市场融资、布局、后续方向及恢复候选。其 `target_delta[8]` 不是只允许一个非零项。不能将它与后来的 Daily DP `family/kind/amount` 接口混为一谈。

| 可搜索权限 | Candidate8 宽版 | 本包当前 C3/F3 RL 覆盖接口 |
|---|---|---|
| 一个产业多档数量 | 有 | 仅一个选定项目 |
| 两、三产业联合 | 有限组合 | 无 |
| 时机、规模、人员土地配套 | 有对应候选或配套修正 | 由原生规划自动决定，RL不单独选择 |
| 市场融资/销售、布局、恢复 | 有对应候选 | 没有开放给RL |
| 真实执行质量 | 必须另验，曾是短板 | 依赖较新的C3/F3执行器，仍非完美 |

旧 Daily DP 的语义包括 KEEP、DEFER_NEW、REBUILD_NEW、REPLACE_NEW、EXPAND_NEW，并有产业和数量参数。曾有约 321 候选的实验配置，**不是官方上限，也不是所有状态恒定 321 条**。

旧池中 `amount` 可一次调整多个项目；但这不自动等于支持“任意三产业＋土地＋雇工＋销售”的任意联合变动。需要检查实际分支，而不能只增加 schema 字段。

当前 C3 内部也保留 [investment_candidates.hpp](src/stage/c3j7/executor/investment_candidates.hpp) 和 J7 配方选择；其控制器类型接近旧 DP，不能据此假定绕过 C3 后续 forecast、renewal、crop_plan 仍语义一致。

## 4. 具体接入位置

### C3 自主 / J7+C3

[c3_policy.cpp](src/c3_policy.cpp) 的每日分支在 `h.plan → h.renewal_plan → h.crop_plan` 后拿到基础计划，然后选改动，再调用订单准备及实时执行。

宽候选适配需明确“候选产生在这三步之前还是之后”，不能先改完又被后一个 planner 覆盖。建议首版沿用此处、只调整尚未投入项目；每候选拥有独立 `core.target / planned_land / plant_not_before` 等计划数据，更新 forecast、采购、工人安排及必要运行记忆。

复制 C3 状态时要特别小心 `Planner` 的回调和指向原对象的 lambda：不能无审计地缓存整个对象再搬移并复用捕获了旧 `this` 的回调。首版可以从 reset 重跑固定前缀，确认正确后再做完整快照克隆。

`c3j7` 的 J7 只是提案/参考来源，底层仍 C3。宽搜索可以将其作为安全 KEEP，而不是把 J7 原动作当唯一可执行真值。

### F3

[f3_policy.cpp](src/f3_policy.cpp) 当前调用 `a.plan`，为每个候选复制 `Memory`，通过 `forecast_ledger.replace` 撤销旧项目完整流、加入新项目；再更新项目、价格和路径状态。

批量改动必须在**同一独立副本**中组合，不应把多个从同一原始账本算出的副本事后相加。多个改动共享容量时，应整体重算现金可行性、地块、作物维护变体、动物喂养日历和人员需求。修改预期不等于已经成交；按真实执行结果回写、下日再规划。

底层路线失效后调用现有重新调度机制；不能让多份旧 `routes/backlog/couriers` 同时保留资源占用。

## 5. 建议恢复顺序

1. KEEP 与单项目候选先逐步对齐本包已验轨迹。
2. 将 `kind + amount` 扩为批量新项目增减、替换、重建；保护既有活资产。
3. 加入小规模多产业联合提案，同时重新编排资金、地块、人员。不要一次 Cartesian product 全枚举。
4. 最后扩展投产时间、土地、用工、销售窗口。每项都有真实行为效果测试。
5. 用 4 训练 seed × 双座位搜索；冻结完整 29 节点经营策略后用至少 32 个未见 seed 双座位复验、逐对手报告。此数量是实验起点，不是胜率已可信的通用统计保证。

## 6. 必须保留的验证

- KEEP 与原底座完整动作、现金一致；新增候选不能悄悄改 KEEP。
- 请求与实际修改分开计数；fallback、重复/无效候选不能当真实探索。
- 真实成功成交、投入、维护、收获、销售与终局结果要能跟踪。
- 相同 reset seed、双方座位、实时对手用于成对比较；不同 seed 不是强行复制同一个农场状态。
- 每条分支拥有模拟器随机状态、己方和对手状态、日期、账本、执行记忆。只克隆棋盘是不完整快照。
- 1 与 16 线程一致、重复批次无跨局污染、改变 day d 不影响 day d 前已执行前缀。
- 搜索标签只用于离线比较；正式在线策略不读取模拟器私有随机种子或真实未来。
- 报告平均/逐对手胜率、现金、分差、异常数、吞吐；不能只报告最优 seed 或搜索训练胜率。

**结论：可以恢复宽候选，但应恢复经营表达能力并适配新执行器，而不是倒退到旧账本、旧编排器或窄 PPO 接口。**
