# P16 JointAFS R1：动物—供料—后继投产联合候选

日期：2026-09-10。实现、官方规则实时对战、源码构建和可迁移交付报告。

## 1. 结论与版本身份

这次已实现结构化联合候选，不是只交付下一步设计。基底是 **P16–T3R1–TakeoverMerged R1**；不是原 P16，不是上轮“停止追晚瓜”的实验分支。原来的38项运行配置逐字节不变，保留动物预测noipa、P16销售/施肥/作物时钟/开局先验、T3运输及维护修复和接管资金修复。未启用新的学习模型，未加入对手身份或固定十二瓜开局判断。

最终代码在三种子开发比较后冻结，五种子确认期间没有修改。**确认集101/110胜（91.82%），同组父版79/110（71.82%）；开发加确认合计150/176（85.23%），父版125/176（71.02%）。** 不得将确认集91.82%改写成全部面板已经达到90%，也不能宣称线上稳定90%。

全部比较是我方默认自主开局，对十一冻结原程序实时对战。没有再次评测我方强制十二甜瓜接管、90场历史固定录像，也未提交Kaggle。

## 2. 实现范围：不再只有参数档位

修改四个策略文件：新增 `policy/joint_bundle_state.hpp`、`policy/joint_candidates.hpp`，修改 `policy/triad.hpp`、`policy/search.hpp`。完整差异见 `JointAFS_R1.patch`；`SOURCE_PROVENANCE.json`保留父版、配置、源码和实验身份。

### 2.1 先保留原方案，再枚举三种结构

每天仍先运行父版原有候选选择，得到KEEP方案。只有KEEP包含尚未购买、尚未放置的新增动物，并且没有正在执行的联合项目时，才生成最多三个额外候选：

| 结构 | 动物投资变化 | 配套作物安排 |
|---|---|---|
| A | 将当日新增动物目标允许上限降低1 | 1块供料小麦＋1轮后继作物 |
| B | 将该上限降低1 | 2块供料小麦＋各1轮后继作物 |
| C | 将该上限降低2 | 2块供料小麦＋各1轮后继作物 |

这里是上限降低后重新组织当天方案，**不是保证其余项目完全不变的精确减一操作**。现有动物、现有作物、已购动物及已投入承诺不能拿来冒充尚未投入的可撤销资金。正常候选生成仍可选择剩余产业。

每个结构在小麦2—4天收获时长、五类后继作物间做有限枚举，调用原有作物周期/维护DP与组合估值筛选；只保留每个结构的一个最好估值。后继只计一轮，不添加无限重复轮作价值。最少还保留KEEP，因此不是一律少养动物或硬禁晚瓜。

这一版是**结构化候选搜索＋局部DP＋共同时域执行比较**，不是全农场全季状态的精确Bellman最优解。预筛会丢掉一些估值不高但真实可能更强的结构。

### 2.2 用同一个供料与后继窗口比较KEEP和新方案

KEEP与每个联合候选使用相同公开对手供给假设，在相同4—6日事件窗口内推进：采购、雇工、移动、维护、收获、入库、出售和后继种植都由现有执行器实际生成动作。下一天恢复共同原生经营策略，但保留联合任务的合法承诺。

必须在条件预演中真实启动需要的后继作物，且没有联合项目取消，才允许候选参与比较。窗口末的估值从模拟出的真实状态重建，不再额外叠加一份“已经许诺的后继收益”。原KEEP也获得相同前瞻窗口，避免只给新方案多算时间。

**预演不是完整未来。** 对手供给、后续需求及交付采用公开信息条件假设；预演不读取真实seed、对手私仓、对手代码或未来商店。本版未解决所有未来预测误差，也没有把后继成本和收益变成无风险保证。

### 2.3 后继不是一条到点盲目执行的脚本

联合状态按真实观察推进：等待小麦播种→实际小麦存活→确认实际收获→最早下一天申请后继→确认后继实际播种。

地块因为干旱消失，不能算作收获；发出过PLANT，不等于已经种成。程序同时检查已发出的HARVEST和下一步地块变化。后继不能借当天未成交的预计收入提前启动。

为后继保留尚缺种子的资金，正常新增投资预算先扣除这部分；后继执行使用实际现金/种子，扣除预留后允许预算为负，避免“先截成0再释放预留”凭空增加钱。启动失败有明确期限和取消原因。这个预留**不是整条后继生命周期的所有工资、饲料和仓储都锁定了**，实际维护仍由原规划器和执行器负责。

小麦实际收获后，联合项目仍活跃时保护最多两轮喂养所需的实际小麦，再按P16销售策略处理余货。不能将未来田里产出当作现货，也没有建立精确到某一批小麦现金收入的独立银行子账户；现有库存会合并。它是可兑现性较强的状态与资金约束，不是完整的商品批次会计系统。

动物上限只作用于联合方案进入的当天，次日恢复正常扩张比较。开发第一版误将此限制延续整个供料期，结果明显退步，已经修正，未交付为默认。

## 5. 它是否真正执行了联合项目？

对保存完整轨迹的88局（每个seed、每个对手只记录对手座位0这一半）检查最终调试计数：共接受95个联合项目，140块供料小麦实际启动并收获，140个后继作物实际启动，95个项目达到后继投产完成条件，取消0次。见`evidence/COMPLETION_TRACE88.json`。

这是88局的范围，不代表另一半座位也逐项审计了，更不代表140轮后继作物全部完成整个季节收益。状态机的“完成”是后继实际投产；之后维护交给共同原生策略。

所记录联合选择出现在第3天或更晚，常见于第3、5、8天；没有要求开局就从六只动物切成固定十二甜瓜。因此目前主要改善的是默认开局后续资本安排，而不是镜像对手首24步。

一个可复核示例：`moon_v215 / 2609125000 / opponent_seat=0`，step192原版仍买一只鹅；联合版保留已有资产，改成新增一块小麦并安排单轮后继甜瓜。调试记录选择3天小麦；step288前已实际收获，step312前已实际开始后继作物。终局分差−621→+4,428。

**这不是证明该例通过“绝不追晚瓜”获胜：它恰好选择了后继甜瓜。** 官方现金复算显示我方现金95,022→76,159，对手95,643→71,731；我方外购小麦费用11,636→10,399、工资6,026→4,725。货物售价、对手回款和后续经营都变化，不能把总翻盘全部归因于省饲料或省工资。

另一个仍胜的`soil_v219g / 2609125001 / opponent_seat=0`中，外购小麦费用反而增加，说明供料安排不是“保证整季外购粮必然下降”。六份样例现金重放满足双方`3000＋所有实收支＝终局现金`且与归档一致；它们是记录动作的会计复核，不是额外六场独立强度样本。见`evidence/cash/`。

## 6. 正确性、编译和耗时

最终源码通过61项新联合合约；另通过30项执行、28项接管、38项交互断言以及P16开局供给先验测试。详见`evidence/build/verified.BUILD.json`。

GCC14.2从最终源码实际重编译，生成与受测库逐字节相同的SHA256；二条新官方完整轨迹1438次自主动作、60个状态检查点一致。将联合宏关闭，原父版两条轨迹1414次自主动作＋24次固定开局动作保持一致。关闭测试包含原有十二瓜前缀，仅证明回退行为，不是新候选的十二瓜接管胜率。

负对照把父版库当成新版，行为检查在step192拒绝。六项评测CLI模拟测试检查3→8只追加、重复不重跑、八种子上限、工作进程上限、不同seed或二进制拒绝混用。模拟测试不冒充真实比赛。

**耗时不可忽略。** 主面板新版本最慢一次调用墙钟2.98355秒，父版最高0.32462秒。对其中最慢的同一比赛做无其他对局并发的重复：新版最大墙钟0.44955秒、CPU0.44910秒，父版0.16532秒；双方动作哈希均与归档一致。这说明并发测量与单进程测量不同，但不能删除2.98秒的原记录，也不能据此保证Kaggle硬件一定不超时。

交付整理后，在新的清洁目录中再次从源码编译，动态库与受测库逐字节相同，并重新通过1438步动作检查。见`evidence/RELOCATED_REBUILD.json`与`evidence/RELOCATED_BEHAVIOR.json`。

本轮没有在线沙箱限时、ABI、完整提交schema认证，没有在GCC13上重编译修改版。现有noipa保护保留；本机换工具链仍需通过构建门。版内编译验证通过只说明一致性，不是线上时间达标。

## 7. 已解决与尚未解决的边界

已实现：小范围跨产业结构替换、供料收获和一次后继的持久承诺、同窗条件比较、真实资金/种子检查、可回退原方案。

没有实现：全季最优产业组合；所有库存/在途货物精确批次归属；后继全部劳工及融资风险预留；未知商店和对手出售时序的准确预测；从任何陌生开局均能保持同等实力。种子资金预留和次日启动是保守防止透支的办法，不是完整金融最优化。

既有对手池、三种子开发及五种子确认支持这是一个值得继续保留的经济候选分支；不支持整体或逐对手稳定90%。本次没有围绕确认集的失败结果继续改参数。

## 8. 复现与使用

Linux x86-64 / WSL2，Python标准库与C++20编译器。入口只用根目录`main.py::agent`或每局独立`main.py::create_agent()`，默认明确加载`policy/joint.so`，不要只替换动态库，不要调用旧包装器默认寻找的agent.so。

```bash
python3 verify_package.py
python3 check_binary.py
python3 build.py --cxx g++ --out build/local.so
```

构建使用临时文件，通过38项ABI、合约和冻结轨迹才生成新输出，不覆盖发布库/父版库，也不自动启动整组对战。换编译器失败时保留日志，不改冻结参考哈希。

```bash
# 三开发种子，父版与新版各66场，共132场
python3 evaluate.py --out runs/local_pair --seeds 3 --workers 3
# 同目录续到八种子，只补后五个，各110场新增，共220场新增
python3 evaluate.py --out runs/local_pair --seeds 8 --workers 3
# 测试自己新编译的库，另建输出目录
python3 evaluate.py --out runs/local_rebuild --binary build/local.so --seeds 3 --workers 3
```

`--seed-start`可指定另一批新seed；不传则使用本报告八个种子。最终每版每对手16场，脚本拒绝超过八种子、混用二进制/配置/seed续跑。不要把重复同一面板当作新增泛化证据。

`panel_small.py`是本轮实际使用的单库面板工具。归档`evidence/panels/`中的原绝对路径保留历史来源，并不要求本机存在这些路径。`research/v1`、`research/v3`是淘汰版本，默认入口不读取；不把它们的结果计入默认库。
