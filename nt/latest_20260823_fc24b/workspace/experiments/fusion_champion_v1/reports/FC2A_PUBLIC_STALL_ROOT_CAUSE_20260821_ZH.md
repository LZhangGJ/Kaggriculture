# FC2A Public 卡死故障复盘（2026-08-21）

## 结论

FC2A 的 1,355.1 Public 分数主要不是策略弱，而是一个确定性的 CPU 融合故障：

> 开局检测到对手羊路线后，FC2A 在第 288 步切换到 PRT；但 PRT 此前没有同步内部状态，接管后漏掉新一天的雇工事务，从第 289 帧开始全 PASS 到终局。

这不是推测。两个 Public 败局具有完全相同的触发条件和完全相同的 431 帧空转尾巴；本地已知失败种子也可逐帧复现。

两场败局在第 288 帧仍有 6牛8羊或10牛4羊；第 289 帧变成：

```text
farmer = PASS
hands = []
market = []
```

之后每天都没有重新雇人，动物陆续逃走，现金固定在约 1.3 万。

## 根因

FC2A 由多个有内部状态的 Python Agent 融合而成。K320、X562/Legacy 前缀会从开局运行，但原版 PRT 只在第 288 步条件成立后第一次被调用。

PRT 不是无状态函数。它需要从第 0 步连续更新路线、日期和事务状态。中途第一次调用，相当于让一个“没看过前 12 天”的 Agent 接管第 13 天，导致日初事务链断裂。

因此根因是：

```text
状态型子策略晚接入
→ 内部状态与官方真实局面不一致
→ 日初 HIRE/现金事务缺失
→ 无 hand
→ 永久 PASS
```

## 修复与官方复验

修复方法不是硬编码第 289 步雇 5 人，而是让 PRT 从开局影子运行；只有输出继续由当前主路线控制。真正切换时，PRT 已拥有和真实对局一致的内部历史。

官方 1.32.7、种子 `545102`、双座位复验结果：

| 版本 | 终局现金 | 对手现金 | 非 PASS 帧 | 最长全 PASS | 第289帧 |
|---|---:|---:|---:|---:|---|
| 原 FC2A | 13,313 | 118,351 | 261 | 431 | 全 PASS |
| Shadow-PRT 修复 | 70,382 | 68,695 | 692 | 10 | 卖牛奶、雇5人、取小麦 |

故障被精确复现，修复通过双座位语义门。

## 为什么原验收误判

原验收只检查：

- 是否跑满 720 帧；
- 双方状态是否 `DONE`；
- 推理时间是否合格。

但一个从中局开始一直 PASS 的 Agent 仍然可以正常 `DONE`。事实上原 Rank14 验收回执已经出现种子 `545102` 仅赚 13,313，却仍被判为 PASS。

后续融合 Agent 必须增加：

1. 已知故障种子逐帧回归；
2. 最长连续全 PASS 监控；
3. 每日雇工和市场事务连续性；
4. 非 PASS 动作帧数；
5. 终局现金相对冻结基线的退化门。

`DONE` 以后只代表协议合法，不再代表策略验收通过。

## 边界

- 本报告只证明 CPU 提交包装器存在并已修复该卡死故障；
- 不据此宣称 FC2A 已达到 90% 全池目标；
- 修复版尚未提交 Public；
- JAX 版使用不同的显式 carry，必须独立审计，不能由 CPU 修复结果自动推定无误。
